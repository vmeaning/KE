# Регламент команды KE

> Статус: **v0.1 · черновик на обсуждение** · 2026-09-29
> KE — сервис управления конфигурационными единицами (КЕ) IT-службы.
> Роли — это Claude в разных режимах: **skills** загружаются в текущую сессию, **subagents** работают в отдельном, независимом контексте. Владелец продукта (ВП) — Юра.
> Места, где нужен ответ ВП, помечены **[?N]** — номер вопроса из обсуждения.

---

## 0. Принципы

1. **Автор не проверяет сам себя.** Независимые проверяющие (тестировщик, ревьюеры, аудитор) — это subagents. Они получают артефакты (Issue, PR, спецификации), но не видят рассуждений автора. Поэтому они не повторяют его ошибок.
2. **Истина — в репозитории и GitHub, а не в чате.** Сессию можно потерять в любой момент. Состояние всегда восстанавливается из Issues, PR, меток и документов в `docs/`.
3. **Сначала контракт, потом код.** Требования, API-контракт, схема данных и макет экрана утверждаются до реализации. Поэтому backend и frontend могут работать параллельно, каждый по своему контракту.
4. **Доказательства вместо утверждений.** «Готово» = команда + её результат, тест + его имя. Отчёт без доказательств недействителен.
5. **Процедура соразмерна риску.** Объём проверок зависит от размера задачи. Обязательные гейты (безопасность, контракт, дизайн) не пропускаются никогда.
6. **Трассируемость.** Требование → критерий приёмки → Issue → PR → тест. У каждого звена есть ID, по которому его можно найти.
7. **Процесс улучшается по данным.** Аудитор измеряет работу команды и предлагает конкретные правки инструкций ролей. Правки вносятся через PR и одобряются ВП.

## 1. Роли

| # | Роль | Как запускается | Главное | Статус |
|---|---|---|---|---|
| 0 | **Владелец продукта (Юра)** | человек | решения из §2; утверждение требований, архитектуры, ТЗ фаз, приёмка | из запроса |
| 1 | **Аналитик** | skill `analyst` | превращает описание ВП в требования: глоссарий, доменная модель, пользователи и роли, user stories, бизнес-правила, критерии приёмки | **новая [?2]** |
| 2 | **Архитектор** | skill `architect` | архитектура и стек, ADR, контракты (API, схема БД), техническая часть ТЗ фазы, проверка декомпозиции, гейт `gate:contract`, приёмка блока | из запроса |
| 3 | **Лид** | skill `lead` | оркестратор: задачи и критерии приёмки, запуск subagents, метки, ревью, merge, эскалации | из запроса |
| 4 | **UI/UX-дизайнер** | subagent `ux-designer` | дизайн-система, спецификации и прототипы экранов, гейт `gate:design` (сверка реализованного UI с макетом) | из запроса |
| 5 | **Backend-разработчик** | subagent `backend-developer` | серверный код + unit/integration-тесты + PR | из запроса («Разработчик») |
| 6 | **Frontend-разработчик** | subagent `frontend-developer` | UI по макету и API-контракту + компонентные тесты + PR | из запроса |
| 7 | **Тестировщик** | subagent `tester` | независимая проверка по критериям приёмки: API-тесты и e2e (Playwright), отчёт в PR | из запроса |
| 8 | **Security-ревьюер** | subagent `security-reviewer` | обязательный гейт `gate:security`: аутентификация, права доступа, секреты, ввод данных, импорт, зависимости | **новая [?3]** |
| 9 | **Аудитор процесса** | subagent `process-auditor` | соблюдение регламента, выборочная глубокая проверка качества, метрики, разбор эскалаций, предложения по улучшению skills и subagents | из запроса (§9) |

**Почему одни роли — skills, а другие — subagents.**
- **Skills** (аналитик, архитектор, лид) ведут диалог с ВП и держат контекст фазы. Поэтому они работают в главной сессии («штаб»), то есть в разговоре с Юрой.
- **Subagents** выполняют ограниченную работу, где важны чистый контекст и независимость: исполнители и проверяющие. Их запускает Лид или исполнитель цикла задачи (§12).

Кроме ролей есть процедурный skill **`task-loop`**. Это не роль, а сценарий «провести одну задачу через цикл §4»: разработчик → CI → тестировщик → доработки → гейты. Лид отдаёт ему задачу и получает её обратно в состоянии «готово к ревью» или «эскалация». Так Лид не держит в контексте подробности каждой задачи.

**Почему нужен Аналитик.** В CADV ТЗ фазы писал Архитектор, потому что предметная область была технической. KE — прикладная система: в ней много понятий (типы КЕ, атрибуты, связи, жизненный цикл, владельцы), ролей пользователей и бизнес-правил. Если требования поймут неправильно, это обойдётся дороже любых токенов. Архитектор при этом должен думать о *как*, а не о *что*. Отдельный skill даёт короткие и сфокусированные инструкции для каждой роли.

**Почему нужен Security-ревьюер.** CMDB хранит карту инфраструктуры: хосты, адреса, владельцев, зависимости. Для атакующего это готовый план атаки. Права доступа, аудит изменений и импорт данных — зоны, где ошибка не видна на обычном тесте.

**Роли, которые пока не нужны** (добавим, когда появятся задачи):
- **DevOps / Release** (skill `devops`) — когда определится целевая среда развёртывания [?4]. До этого CI и `docker-compose` для локального запуска делает разработчик в фазе 0.
- **Технический писатель** — пользовательская документация. На старте её ведёт Аналитик.
- **Отдельный e2e-тестировщик** — на старте e2e делает `tester`. Аудитор скажет, если одному тестировщику станет тяжело.

## 2. Решения, зарезервированные за ВП

ИИ **никогда** не принимает эти решения сам. Роль готовит материалы и рекомендацию, а решает Юра. Решение фиксируется в шапке документа (`Статус: approved · дата`) и в PR, через который документ попадает в `main`.

1. Утверждение требований (`docs/requirements/`), ТЗ фаз и изменений в `docs/ARCHITECTURE.md`, включая выбор стека (ADR).
2. Утверждение дизайн-системы и ключевых экранов [?8].
3. Состав и порядок фаз (roadmap), перенос фич между фазами.
4. Подтверждение приёмки фазы.
5. Изменения этого регламента и инструкций ролей (`.claude/**`) [?6].
6. Всё необратимое или внешнее: удаление данных, доступы и секреты, публикация, платные сервисы, зависимости с не-permissive лицензией.
7. Вопросы по требованиям, которые эскалировал Лид (`needs-po`).

## 3. Жизненный цикл

```
A. Discovery (один раз, дальше — инкрементально)
   ВП: описание ──► Аналитик: вопросы ВП ──► docs/requirements/ ──► ВП утверждает

B. Архитектура (один раз, дальше — через ADR)
   Архитектор: ARCHITECTURE.md + ADR (стек [?10]) + roadmap фаз ──► ВП утверждает
   Дизайнер: дизайн-система (docs/design/) ──► ВП утверждает

C. Фаза N (повторяется)
   C1. ТЗ фазы docs/phases/phase-N-<name>.md:
       функциональная часть (Аналитик) + техническая часть и контракты (Архитектор) ──► ВП утверждает
   C2. Лид: Issue фазы + задачи (Definition of Ready) ──► Архитектор: проверка декомпозиции (один проход)
   C3. Дизайн-задачи идут первыми: макеты экранов фазы ──► ВП утверждает ключевые [?8]
   C4. Цикл задачи (§4) — для каждой задачи
   C5. Конец фазы: Аудитор (ретро, §9) ──► Архитектор: приёмка блока ──► ВП подтверждает
       ──► правки процесса по итогам ретро (PR type:process) ──► ВП одобряет
```

**Фаза 0 (bootstrap)** начинается сразу после утверждения архитектуры: каркас репозитория, CI (lint, typecheck, тесты, сборка, e2e smoke), локальный запуск (`docker-compose`), раздел «Инженерные правила» в `CLAUDE.md` с точными командами. В фазе 0 задачи идут последовательно.

## 4. Цикл задачи

```
Лид: Issue (status:ready, DoR ✓) ──► task-loop
  ──► разработчик (backend | frontend): ветка + код + тесты + самопроверка ──► PR «Closes #N» (draft → ready)
  ──► CI зелёный; находки Claude Code Review разобраны разработчиком [?11]
  ──► Тестировщик: отчёт в PR
        ├─ PASS ─► гейты по меткам: security / contract / design ─► Лид: ревью ─► squash-merge
        └─ FAIL ─► status:rework + rework-N ─► разработчик
                   FAIL при метке rework-3 ─► тестировщик ставит escalated ─► Лид решает (§6)
                                                                          + Аудитор разбирает причину
```

Красный CI после первого push и находки бота разработчик исправляет **до** передачи тестировщику. Это его собственный цикл, он не считается доработкой.

Задачи `type:design` и `type:docs` идут без тестировщика: результат проверяет Лид по чек-листу роли, ключевые экраны утверждает ВП [?8].

### 4.1 Definition of Ready (задачу можно брать в работу)
- Критерии приёмки проверяемы и пронумерованы (`AC1`, `AC2`, …).
- Разделы ТЗ, контракта (OpenAPI, схема) и макета, на которые ссылается задача, существуют и утверждены.
- Задачи, от которых она зависит, смержены.
- Проставлены размер (≤ M) и метки гейтов.

### 4.2 Definition of Done (задача готова)
- Каждый `ACn` подтверждён тестом или воспроизводимой командой. В тесте есть ссылка `#N ACn`.
- CI зелёный. Нет новых предупреждений линтера и типизации. Нет пропущенных тестов (`skip`) без Issue.
- Тестировщик дал `PASS`. Все обязательные гейты дали `APPROVE`.
- Лид провёл ревью. Документация и контракт обновлены, если поведение изменилось.
- PR смержен, Issue закрыт с `status:done`.

### 4.3 Размер задачи определяет объём процедуры

| Метка | Что это | Цикл |
|---|---|---|
| `size:S` | опечатка, мелкий фикс, документация | разработчик → CI → тестировщик (облегчённо: без новых тестов, проверка AC и прогон) → merge |
| `size:M` | обычная задача | полный цикл |
| `size:L` | крупная — Лид обязан разбить её на M | — |

**Гейты не пропускаются никогда, независимо от размера:**

| Метка | Когда ставится | Кто проверяет |
|---|---|---|
| `gate:security` | аутентификация и авторизация, RBAC, секреты, обработка пользовательского ввода, импорт и экспорт данных, интеграции, новые зависимости, журнал аудита | `security-reviewer` |
| `gate:contract` | изменение API-контракта, схемы БД или миграций, доменной модели, межмодульных интерфейсов | Архитектор |
| `gate:design` | новый экран или изменение раскладки и сценария на существующем экране | `ux-designer` (сверка со спецификацией по скриншотам) |

### 4.4 Правила против бесконечного пинг-понга
- При повторной проверке тестировщик проверяет: все `ACn`, ранее найденные баги и регрессию. **Новые** замечания вне AC уровня `minor` не дают `FAIL`. Они уходят в follow-up Issue.
- Тестировщик не добавляет критерии приёмки. Если AC неполны, он пишет об этом Лиду, и это не считается провалом разработчика.
- Каждый баг описан воспроизводимо: шаги, ожидаемый результат, фактический результат.
- Для бага разработчик сначала пишет тест, который падает, и только потом исправляет код.

## 5. Параллельная работа

- Фаза 0 — строго последовательно.
- Дальше Лид может вести **до 3 задач одновременно** [?13], если они не трогают одни и те же модули. Каждая задача идёт в изолированном окружении: отдельный git worktree или отдельный поток (§12).
- Backend и frontend одной фичи идут параллельно, если API-контракт уже утверждён (frontend мокает API по OpenAPI).
- Разрешение merge-конфликтов не считается доработкой и не увеличивает счётчик `rework-N`.

## 6. Эскалация

- Любой возврат PR разработчику — `FAIL` тестировщика, `CHANGES REQUIRED` гейта или замечание в ревью Лида — добавляет следующую метку: `rework-1` → `rework-2` → `rework-3`. Счётчик единый [?15]. После доработки PR снова идёт к тестировщику (регрессия) и к тому гейту, который вернул задачу.
- Если тестировщик находит баги в PR с меткой `rework-3`, он ставит вердикт `FAIL — ESCALATED` и метку `escalated`. Четвёртого круга нет. Лид выбирает один из вариантов:
  1. переформулировать или разбить задачу;
  2. передать Архитектору, если проблема в дизайне решения;
  3. спросить ВП (`needs-po`), если проблема в требованиях;
  4. перезапустить задачу со свежим разработчиком и сводным брифом («что пробовали, что не сработало»).
- На каждую эскалацию `process-auditor` делает короткий разбор первопричины: нечёткие AC, халтура исполнителя, придирки проверяющего или дефект инструкции. Выход разбора — предложение правки.
- Если разработчик видит противоречие в постановке, он **останавливается** и возвращает вопрос Лиду (метка `blocked`). Такой возврат не расходует круг `rework`.

## 7. Передача работы между ролями

**Бриф Лида для subagent** (минимум, который нужен для работы; остальное subagent читает сам):
```
Role: <agent>  Task: #N  Branch: <branch>  Round: initial | rework-K
Read: CLAUDE.md, Issue #N, <spec §>, <contract>, <design spec>
Previous report: <link to PR comment>   (для доработки)
Constraints: <что нельзя трогать>
Return: <формат ответа — см. инструкцию роли>
```

**Ответ subagent Лиду** — не длиннее ~15 строк: статус, ссылки, доказательства (команды и итоговые строки их вывода), открытые вопросы. Подробный отчёт живёт в комментарии PR, а не в контексте Лида. Так главная сессия не переполняется.

## 9. Аудитор процесса

**Зачем.** Каждая проверка в цикле задачи смотрит на одну задачу. Никто не смотрит на систему целиком: повторяются ли одни и те же ошибки, не пишут ли тесты «для галочки», не ставит ли тестировщик `PASS` не глядя, не отходят ли роли от правил. Аудитор закрывает эту дыру. Кроме того, он превращает наблюдения в правки инструкций.

**Когда запускается** [?5]:
1. на каждую эскалацию (`escalated`) — короткий разбор первопричины;
2. в конце фазы — полное ретро;
3. по запросу ВП или Лида — в любой момент;
4. если фаза длинная — промежуточный аудит каждые ~10 смерженных задач.

**Что проверяет:**
- **Соблюдение регламента:** не было merge без `PASS` или гейта; метки и счётчики `rework` ведутся честно; Issues соответствуют DoR; отчёты соответствуют формату и содержат доказательства.
- **Качество (выборочно, 20–30% PR фазы):** перезапускает тесты; проверяет, что тесты действительно проверяют поведение (мутационная выборка: ломает код локально, падает ли тест); ищет ослабленные assert, лишние моки, `skip`, «зелёные» тесты без проверок; проверяет, что заявления в отчётах совпадают с реальностью.
- **Эффективность:** доля задач, принятых с первого раза (first-pass yield); среднее число кругов `rework`; доля красного CI на первом push; число эскалаций и их причины; дефекты, найденные после merge (метка `escaped`); scope creep.

**Результат:** отчёт `docs/audit/phase-N-retro.md` (или `escalation-<N>.md`):
- метрики и их динамика относительно прошлой фазы;
- нарушения со ссылками;
- первопричины;
- **предложения по улучшению**, каждое в формате: проблема → доказательство → конкретный diff инструкции → ожидаемый эффект → как измерим.

Аудитор **не правит** код и инструкции, он пишет только свои отчёты. Предложения применяет Лид через PR `type:process`, одобряет ВП [?6].

| Размер | `size:S`, `size:M`, `size:L` |
| Гейты | `gate:security`, `gate:contract`, `gate:design` |
| Статус | `status:ready`, `status:in-progress`, `status:testing`, `status:review`, `status:rework`, `status:blocked`, `status:done` |
| Эскалация | `rework-1`, `rework-2`, `rework-3`, `escalated`, `needs-po` |
| Качество | `escaped` — баг найден после merge в коде, который прошёл проверку |

`type:spike` — исследование с ограничением по времени (например, выбор библиотеки). Результат спайка — выводы или черновик ADR, без продакшн-кода.

## 11. Ветки и merge

- Основная ветка — `main`, защищена: только через PR и только с зелёным CI [?12].
- Каждая задача — отдельная ветка `task/<N>-<slug>` и PR в `main`. Документы штаба (требования, ТЗ, ADR) идут отдельными PR `type:docs`.
- **Merge делает Лид** (squash), если выполнены все условия:
  - CI зелёный;
  - отчёт тестировщика `PASS`;
  - все гейты по меткам дали `APPROVE`;
  - Лид провёл ревью.
- Разработчик свой PR не мержит. Merge с красным CI или непройденным гейтом запрещён, даже для `size:S`.

## 12. Как это запускается

**Штаб** — главная сессия, в которой Юра разговаривает с командой. В ней по очереди работают skills `analyst`, `architect`, `lead`. По умолчанию штаб действует как Лид. Новая сессия штаба восстанавливает состояние из трекинг-Issue фазы и меток.

**Цикл задачи** (`task-loop`) может идти в разных местах. Это зависит от среды [?1]:

| Режим | Где идёт цикл задачи | Плюсы | Минусы |
|---|---|---|---|
| **A. Claude Code Projects** (облако) | отдельный поток (thread) на каждую задачу: своя ветка и PR, внутри — subagents | параллельность, работа с телефона, панель Overview, события PR | beta, только планы Pro/Max |
| **B. Облачные сессии** (как сейчас) | штаб создаёт отдельную облачную сессию на каждую задачу | как у A | больше ручной координации, нет Overview |
| **C. Локально** (Desktop «Local» или CLI) | subagents в отдельных git worktree внутри штаба | проще всего, нет ограничений на ветки | компьютер должен работать |

Почему нельзя всё делать в одной облачной сессии: в облаке `git push` разрешён только в ветку текущей сессии. Поэтому в облаке каждой задаче нужен свой поток или своя сессия со своей веткой.

**Технические предохранители.** Правила в инструкциях дополняются механическими запретами. Их нельзя «забыть» или обойти:
- hooks в `.claude/settings.json` блокируют push в `main`, `--force` и `--no-verify`;
- subagents не могут править `.claude/**` и этот регламент — такие правки делаются только в PR `type:process`;
- у ревьюеров нет инструментов записи (`Edit`, `Write`); аудитор может писать только в `docs/audit/`;
- тестировщик не может править продакшн-код, только тесты;
- CI отклоняет пропущенные тесты (`skip`, `only`) без ссылки на Issue.

**Как ВП в курсе.** У каждой фазы есть трекинг-Issue: чек-лист задач, их статусы, ссылки на PR и открытые вопросы к ВП. Лид обновляет его после каждого события [?16].

**Модели.** По умолчанию все роли работают на лучшей доступной модели (`model: inherit`). Аудитор может предложить перевести рутинные роли на более дешёвую модель, если данные покажут, что качество от этого не падает [?14].

## 13. Язык

## 14. Изменение регламента

Регламент и инструкции ролей версионируются. Любая правка идёт через PR `type:process` со ссылкой на причину (ретро, эскалация, решение ВП). Merge разрешён только после одобрения ВП. После правки номер версии в шапке этого документа увеличивается.
