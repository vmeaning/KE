# S1. Описание системы от ВП (исходный текст)

> Получено от ВП 2026-10-07. Текст сохранён без изменений. Требования ссылаются на него как `[S1 ¶N]`, где N — номер абзаца.

**¶1.** Ниже описание системы, которую нам надо будет сделать. Внимательно изучи, предлагай корректировки, правки и т.д. Я не боюсь критики, мне важно, чтобы получилось решение, которые будет удобно и эффективо решать задачи по управлению конфигурационными единицами, их жизненным циклом, и так далее.

**¶2.** Я мог что-то упустить в описании, поэтому не стесняйся дополнять пробелы исходя из опыта арзитектора и глядя на систему глазами IT-директора.

**¶3.** Система будет управлять конфигурационными единицами (КЕ), отслеживать их жизненный цикл, формировать уведомления и задачи в таск-трекеры (Яндекс трекер, Jira) при необходимости произвести какие-то действия, регламентные процедуры и т.п. с КЕ. Система будет опираться на принципы ITIL.

**¶4.** Исходный запрос от вероятного заказчика системы был на систему управления жизненным циклом информационных систем (ИС), но мы будем делать универсальное решение для управления КЕ разных типов (в том числе и ИС), и будем проектировать и реализовывать гибкую настраиваемую систему с разделением базового слоя и конфигурационного слоя, чтобы заказчик мог экспортировать свои настройки (настройки справочников, их содержимое, кастомные настройки вида карточек КЕ для конкретных типов и т.п.) и применять на "чистой" системе (с помощью встроенной утилиты импорта конфигурации). Также такой архитектурный подход сделает обновление системы более лёгким и безопасным с точки зрения риска потери данных и настроек.

**¶5.** Все действия с КЕ записываются в историю этой КЕ. Доступ к истории КЕ может быть ограничен для пользователей. Для пользователя можно будет назначить ему роль, для ролей определяется доступный роли scoup функциональности (разделы сервиса). Для ролей задаются CRUD-права на объекты системы. У администратора системы должна быть возможность массового назначения ролей пользователям. Одному пользователю можно назначить более одной роли. При сложении ролей разрешения побеждают запреты.

**¶6.** Про доступный пользователям scoup и роли: кажется полезным определять какие типы КЕ будут доступны пользователю, при этом типы КЕ можно добавлять в справочник типов КЕ. Для новых добавленных в справочник типов КЕ в настройках ролей по умолчанию появляется строка с новым типом КЕ и выставляются пустые права - снятые галочки по всем колонкам (Create, Read, Update, Delete) для всех ролей, кроме администратора, и в разделе определения скоупа для роли так же добавляется строка с новым типом КЕ, и галочка у этой строки тоже снята у всех ролей, кроме администратора. Т.о. при создании нового Типа КЕ он не будет сразу виден всем пользователям, можно будет спокойно настроить вид карточки для нового типа и, если требуется, завести карточки активов (КЕ) нового типа и только потом сделать активы доступными для всех пользователей или для определенных ролей.

**¶7.** В системе можно будет заводить КЕ, заполнять данные в карточках конкретной КЕ (для каждого Типа КЕ состав полей карточки и их обязательность может быть разный). При добавлении в настройках системы (в справчник типов КЕ) нового Типа КЕ, у него (у этого нового типа) будет шаблон карточки Типа КЕ по умолчанию - набор полей, которые есть у всех КЕ. Далее Администратор сможет добавить произвольные поля разного типа, назначать поля обязательными для заполнения (важно учесть кейс, что поля в шаблон можно будет добавить уже после того, как в систему добавлены КЕ данного типа, и если добавить новое обязательное поле, которого ранее не было, или ранее необязательное поле сделают обязательным, то это не должно нарушитьработу системы. Если после описанных манипуляций зайти вкарточку и попытаться её сохранить, то интерфейс потребует заполнить новые обязательные поля, но до этого добавление новых полей не должно сломать систему), группы (чтобы объединять поля в группы), разделители (например, горизонтальная линия), текстовые блоки для подсказок или наименований групп, возможно что-то ещё надо предусмотреть в конструкторе/редакторе шаблонов карточе для типов КЕ, предложения приветствуются. Дефолтные поля удалять нельзя - они общие для любого Типа КЕ.

**¶8.** *Добавленные поля будут иметь системные id, назначаемые автоматически при создании, но их можно будет изменить (или создать к ним алиасы, чтобы алиас более понятно для человека отражал назначение полей), эти системные id можно будет использовать при формировании кастомной логики алертов. Эта тема пока под вопросом, посмотрим по ходу описания системы пригодится ли такая фича*.

**¶9.** Удалять кастомные поля из шаблона можно только если не сохранено ни одной КЕ данного типа, если таковые уже есть, что удаление полей недопустимо. В связи с этим, про открытии шаблона карточки Типа КЕ надо предупреждать пользователя, что добавленные на карточку поля невозможно будет удалить, если в системе есть хотя бы одна КЕ данного типа. При этом не содержащие данных оформительские элементы карточки - разделители, текстовые блоки, удалять можно и при наличии в системе сохранённых КЕ данного типа.

**¶10.** Для Типа КЕ можно задать список ответственных из числа пользователей системы. Эти ответственные будут выводить в списке ответственных, которых надо будет уведомлять о регулярных мероприятиях по КЕ (об этом ниже), плюс форма поиска произвольного пользователя в системе. Если в настройках Типа КЕ при задании списка ответственных поставить галочку, "Только указанные ответственные", то форма поиска при настройке регулярных мероприятий появляться не будет. Если в настройках Типа КЕ список ответственных пуст, то при настройке регулярного мероприятия выводится просто возможность поиска сотрудника.

**¶11.** При работе с КЕ можно будет добавлять в карточке (на отдельной вкладке или на одном экране - это вопрос, который надо продумать) сколько надо регулярных (повторяемых) регламентных мероприятий (зможно назвать по другому, если есть более принятый термин в ITIL в даном контексте): добавлятся строка, задаётся имя мероприятия/активности, дата последнего мероприятия (эта дата или в прошлом - проведённое ранее мероприятие, или отсутствует, если мероприятия ещё не проводились), и задаётся дата следующего регламентного мероприятия - в будущем: задать можно или прямо указав дату, или указав через сколько дней после предыдущего мероприятия, тогда дата считается автоматически; Ответственный - выбирается из справочника пользователей в системе (или из числа настроенных для данного Типа КЕ Ответственных), ему будет приходить уведомление. При подтверждении/сохранении нового добавляемого мероприятия - переход в диалог настроек (позже в него можно будет попасть нажав на иконку настройки - типа шестерёнка, например, справа от строки мероприятия): Обязательное описание результатов мероприятия (чекбокс), Нужна электронная подпись (чекбокс) - если нужна, то необходимо будет подписать подтверждение проведения мероприятия иначе не даст сохранить, Уведомления - чекбокс, если выбран - выбор из настроенных способов уведомления, выбор за сколько дней до даты отправлять уведомление (выбрать можно до трёх дат, например - за 30 дней и за 3 дня); можно добавить несколько алертов с различными параметрами, Задача - если настроена интеграция с Ядекс.Трекером, с Jirа, то можно выбрать кому поставить задачу, за какой срок до даты, какой текст задачи, можно вставить ссылку на КЕ, можно добавить несколько задач с разными параметрами.

**¶12.** Идея в том, что после наступления даты регламентного мероприятия (например, технического обслуживания, проверки состояния, и т.п.) Ответственному за мероприятие будет направлено уведомление (уведомления) и направлена задача в тасктрекер, в соответствие с настройками мероприятия, и у мероприятия появится красная кнопка типа "Подтвердить выполнение мероприятия" (доступная Ответственному и пользователям с ролью Администратора) при нажатии на которую будет выводиться диалог с датой проведения мероприятия - заполненной плановой датой (можно изменить, тогда и расхождение между плановой и фактической датой будет записано в историю этой КЕ), датой следующего планового регламентного мероприятия (если она задавалась в карточке как "через Х дней", то здесь дата также посчитается автоматически, но может быть скорректирована - будет показан чекбокс, что дата следующего мероприятия - это через Х дней, и так же как и в карточке можно будет снять галку и вручную задать время следующего мероприятия. Изменения типа расчета/указания даты также логируется в историю карточки - кто и что сделал), опциональным (или обязательным - задаётся в настройках мероприятия) полем для описания результатов проведения мероприятия, кнопкой "Подписать" для подписания ЭЦП (если в настройках мероприятия выбрано, что подпись обязательна, то без неё сохранить подтверждение проведения мероприятия будет невозможно).

**¶13.** В настройках шаблона карточки конкретного Типа КЕ кроме настройки полей в карточке, можно будет задать регулярные мероприятия, которые будут по умолчанию у всех КЕ данного типа, выставить признак - обязатльно ли их заполнять для каждого КЕ или нет. Например, если Тип КЕ - "Информационная система", то может быть добавлено мероприятие "GxP Валидация", но выставлена галочка, что оно не обязательное, т.к. не все ИС обязаны проходить валидацию по GxP/GAMP.

**¶14.** Также, можно задавать для КЕ разовые запланированные мероприятия, для того, чтобы сформировать алерт-уведомление, постановку задачи в таск-трекер по нерегулярным задачам, связанным с КЕ. Работа с разовыми задачами аналогично работе с регулярными, только не требуется задавать дату следующего подобного мероприятия при подтверждении его завершения. Нерегулярные мероприятия лучше групиировать в интерфейсе отдельно от регулярных, чтобы не путались. Завершённые разовые мероприятия после Х дней лучше скрывать из интерфейса, оставив ссылку/кнопку "Просмотреть завершённые", при нажатии на которую можно будет ознакомиться со списком завершенных разовых мероприятий, и изучить детали по каждому из них. Важно в таких списках предусмотреть компонент с пагинацией, ибо со временм любой список может стать слишком длинным.

**¶15.** Просроченные мероприятия в карточке КЕ подсвечивать красным. Саму КЕ, у которой есть просроченные мероприятия, в списках КЕ подсвечивать красным. Те, у кого срок завершения какого либо мероприятия наступает в ближайшие дни (число дней заданно в настройках системы), подсечивать бледно желтым, например.

**¶16.** Также среди дефолтных возможностей карточки КЕ будет возможность добавлять связи с другими КЕ. При добавлении связи (точнее при сохранении карточки КЕ с новой добавленной или изменённой связью), у КЕ с которой установили связь в интерфейсе появится связь с той КЕ, из карточки которой эту связь создали, при этом эта связь будет зеркальным отражением той, которую устанавливали из исходной КЕ. Например, в карточке КЕ информационной системы (ИС) для работы с договорами установили связь "Входит в" с КЕ общей корпоративной ИС и сохранили карточку; в карточке КЕ общей корпоративной ИС появилась связь с ИС по договорам, и тип связи - "Состоит из" или "Включает в себя" (список видов связей обсуждается, предпочтительней сделать его в виде справочника: название связи, тип связи - односторонняя или двусторонняя, вес). Для связи можно установить вес - значение от 0 до 100; отсутствие веса считается нулём.

**¶17.** При заведении КЕ в систему заполненные поля карточки КЕ сохраняются как Baseline (исходное состояние) для данной КЕ. При сохранении, если baseline у КЕ отсутствует, выводится вопрос, что "сохранить карточку как Baseline?". Варианты ответа: Сохранить Baseline / Сохранить без Baseline / Отменить сохранение. Если у карточки КЕ нет Baseline, то такой пункт должен быть где-то в меню карточки - не на видном месте, а где-то типа "Свойства" и там "Добавить Baseline" (если его ещё нет), если Baseline уже есть, то появляется пункт меню "Изменить Baseline" - виден только для определённой роли: руководитель или кто-то типа того. Естественно, изменение Baseline (когда, кто, что было, что стало) логируется в логе "Audit trail" - он же "Контрольный след".

**¶18.** Должна быть возможность привязать к КЕ документы: непосредственно загрузить документ, скан, или добавить документ как ссылку - аказать название документа и ссылку на него.

**¶19.** Электронные подписи: галка необходимости, подумать где именно они нужны обычно в таких системах. Как вариант при Change Control - утвердить изменение, изменение статуса, факт проведения регламентного мероприятия.

**¶20.** Контрольный след - неизменямый лог, который никому менять нельзя. Пишет все важные события с объектами системы: когда, кто, что сделал, что было, что стало. Как обеспечить его неизменяемость?

**¶21.** Справочник типов алертов-уведомлений: телеграм (требует токен бота), MAX (токен бота), e-mail (smtp, IMAP), куда ещё? Если в мероприятии настроено уведомление в телеграм, но в профиле сотрудника в профиле не указан его телеграм-аккаунт, то ему ничего не уйдёт. Тоже самое и про прочие способы уведомлений. Учесть обработку ошибок для каждого типа уведомления: Х повторный попыток отправки, с паузой ХХ.

**¶22.** Контроль изменений. Когда в инфраструктуру вносят правки (устанавливают обновление, заменяют компонент), процесс управления конфигурациями следит, чтобы изменения проходили через процедуру одобрения. Цель — не допустить неожиданных сбоев и сохранить целостность системы. Для этого мы можем предусмотреть в настройках Типа КЕ галочку, которая будет включать обязательно согласование всех изменений с указанной ролью - Роль "Согласующий изменения должна быть в системе предусмотрена, и должен быть контроль, что это роль только с одним участником. Если галочка включена, то при сохранении изменений в карточке КЕ (вручную или по интеграции, должна быть возможность установить в настройках, что изменения по API всегда принимаются автоматически), указанной в настройках Типа КЕ роли приходит уведомление (внутри системы и на e-mail) с описанием то меняется, и выбором принять изменения, или отменить, если отмена, то инициатору измеений направляется уведомление в систем (типа иконка Колокольчик) с описанием отказа.

**¶23.** Если пользователь присвоена роль Согласующй изменения, то в интерфейсе у него должен появиться Inbox для такого рода запросов на изменения, и в "колокольчик" будут приходить соответствующие уведомления.

**¶24.** Т.к. хочется продавать продукт как "коробочное решение", и минимально заниматься внедрением, то надо продумать, что надо заложить в систему, чтобы заказчик мог самостоятельно интегрировать её с различными корпоративными системмами, AD, и т.п. Например, реализовать API (с авторизацией), по которому можно будет забирать данные их системы как из мастер-системы по КЕ, тот же API или другой механизм, который позволит обновлять состояния КЕ, их атрибуты, данные в карточках, что-то что позволит интегрироваться с AD и аналогичными системами для аутентификации, для загрузки пользователей и групп безопасности, с 1С:ЗУП для загрузки пользователей и т.п.

**¶25.** Кажется, что основным интерфейсом дял работы с системой будет реестр КЕ. Там должны быть фильтры по типам КЕ, статусам, пагинация, экспорт в csv, excel; значения фильтров у пользователя дожны запоминаться. Выводятся только те типы КЕ, которые включены в скоуп роли пользователя. Надо предусмотреть минимальную функциональность виджетов: выводить данные о количестве КЕ, количестве требующих внимание (просроченные мероприятия и т.п.). В последствии при развитии системы вероятнее всего надо будет делать и графические виджеты, и системы дашбордов, которые пользователь настраивает для себя, но пока я не очень понимаю что именно в таких системах надо выводить, и поэтому не готов сформуировать: или оставим на потом, или предлагай варианты принятые в такого рода системах.

**¶26.** Дизайн должен быть коммерческим, современным, адаптивным. Т.к. мы делаем "коробку", что всё что нужно должно быть настраиваемо: справочники, цвета, возможности, ограничения, и т.п.
