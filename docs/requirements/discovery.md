## 1. Как я понял продукт

1. **Универсальная CMDB для IT-службы** по принципам ITIL: учёт КЕ любых типов, их жизненного цикла, связей и истории [S1 ¶3–4].
2. **Плановые мероприятия по КЕ** — главный «двигатель» пользы: регулярные и разовые мероприятия, уведомления, задачи в Яндекс Трекер и Jira, подтверждение выполнения, при необходимости с электронной подписью [S1 ¶11–14].
3. **Гибкость без программирования**: типы КЕ, конструктор карточек, справочники, роли, цвета [S1 ¶7, ¶26].
4. **Два слоя**: базовый слой (продукт) и конфигурационный слой (настройки заказчика). Конфигурацию можно выгрузить и загрузить в «чистую» систему, обновления продукта её не ломают [S1 ¶4].
5. **Готовность к регулируемой среде (GxP)** через настройку, а не через отдельную версию: контроль изменений, электронная подпись, неизменяемый контрольный след, baseline [S1 ¶17–22], [S2].
6. **Коробочный продукт**: заказчик сам подключает AD/LDAP, кадровую систему, таск-трекеры и свои системы через API [S1 ¶24].
7. **Главный рабочий экран** — реестр КЕ с фильтрами, экспортом и виджетами «что требует внимания» [S1 ¶25].

**Поля по категориям** [S2]:
- Компьютеризированная система: версия, дата окончания лицензии, класс по GAMP 5 (1/3/4/5), имя сервера.
- Оборудование: серийный номер, модель, дата окончания гарантии.

У нас это не код, а **поля шаблона** в отраслевом пакете конфигурации (вопрос 12). Даты окончания (лицензия, гарантия) — это «контролируемые даты» с уведомлениями (P-8).

## 3. Фарма (GxP) как настройка универсального продукта

**Принцип:** в ядре нет кода «для фармы». Есть общие механизмы: контролируемые поля, обязательные мероприятия, ЭП на действиях, статусные переходы с условиями, неизменяемый контрольный след. **GxP-пакет конфигурации** включает их так, как требуют нормы. Заказчику без GxP всё это просто не нужно включать.

| Требование [GxP] | Механизм ядра | Что настраивает GxP-пакет |
|---|---|---|
| Актуальный перечень компьютеризированных систем и их GMP-функций (Annex 11 §4.3) | типы КЕ, реестр, экспорт | тип «Компьютеризированная система» с полями: GxP-значимость (GMP/GDP/GLP/GCP/GVP), категория GAMP 5, влияние на качество, безопасность пациента и целостность данных, статус валидации |
| Валидация по жизненному циклу; документы URS, оценка рисков, DQ/IQ/OQ/PQ, отчёт о валидации [S2] | мероприятия с вложениями; документы на КЕ | разовые мероприятия «Квалификация IQ/OQ/PQ», виды документов |
| Периодический пересмотр (Annex 11 §11) | регулярные мероприятия, обязательность по типу [S1 ¶13] | мероприятие «Периодический пересмотр» (обязательное, с ЭП) |
| Регулярная проверка контрольного следа (Annex 11 §9) | регулярные мероприятия | мероприятие «Проверка контрольного следа» |
| Управление доступом (Annex 11 §12) и периодический пересмотр прав (руководства по целостности данных) | регулярные мероприятия | мероприятие «Пересмотр доступов» |
| Резервное копирование и проверка восстановления (Annex 11 §7) | регулярные мероприятия | мероприятие «Тест восстановления из резервной копии» |
| Управление изменениями и конфигурацией (Annex 11 §10) | контроль изменений, baseline | контроль изменений включён для GxP-типов |
| Причина изменения GxP-данных (Annex 11 §9) | обязательное поле «Причина изменения» при сохранении | включено для GxP-типов, P-5 |
| Контрольный след: кто, когда, что, было/стало; прежнее значение не затирается (Part 11 §11.10(e)) | неизменяемый контрольный след [S1 ¶20] | — (всегда в ядре) |
| Электронная подпись: имя, дата и время, значение подписи, неотделимость от записи, два компонента идентификации (Part 11 §11.50, §11.200; Annex 11 §14) | ЭП на действиях | ЭП на мероприятиях, утверждении изменений, переходах статуса, baseline |
| Уникальные учётные записи, блокировка, тайм-аут сессии, политика паролей (Part 11 §11.300) | безопасность ядра | строгие значения параметров |
| Оценка поставщиков (Annex 11 §3) | поля и документы КЕ, справочник организаций | поле «Оценка поставщика» и вид документа «Отчёт об аудите поставщика» |
| Вывод из эксплуатации и архивирование (Annex 11 §17) [S2] | статус «Выведена», запрет удаления | переход с ЭП и обязательным мероприятием «Архивирование данных» |
| Инциденты (Annex 11 §13) | ссылки на внешние обращения | — (Could, P-17) |

Вывод: если ядро даст эти механизмы, фарма-заказчик получит соответствие **настройкой**, а остальные заказчики — ничего лишнего.

## 4. Замечания к описанию и предложения

Формат: `P-n` — предложение. По каждому нужно решение ВП: «принять / отклонить / обсудить». Самые важные вынесены в вопросы §7.

**P-1. Не хватает жизненного цикла КЕ** (вопрос 2). В описании нет статусов КЕ, а это суть CMDB по ITIL: «Планируется → Внедрение/Валидация → В эксплуатации → На обслуживании → Выведена из эксплуатации → Списана». Предлагаю настраиваемую статусную модель на тип или категорию:
- статусы;
- разрешённые переходы;
- кто может переводить;
- условия перехода: заполнены поля, выполнены обязательные мероприятия, нужна ЭП.

**P-2. «Согласующий изменения» — ровно один человек = единая точка отказа** (вопрос 4). Отпуск или болезнь — и все изменения встают. Предлагаю:
- согласует любой участник роли, а их может быть несколько;
- **автор не может согласовать своё изменение** (принцип «четырёх глаз», требование GxP);
- замещение на время отсутствия.

**P-3. Что согласовывать** (вопрос 3). Согласование «всех изменений» утомит пользователей: исправление опечатки в описании ждёт одобрения. Как в [S2], предлагаю флаг «контролируемое поле» в шаблоне и контролируемые переходы статуса. Остальное сохраняется сразу и пишется в историю.

**P-4. Ожидающие изменения и параллельная работа.** Пока по КЕ есть неутверждённый запрос, второй запрос на ту же КЕ не создаётся. Карточка показывает плашку «Есть изменения на согласовании» и разницу «было → станет». Неконтролируемые поля редактировать можно.

**P-5. Причина изменения.** Для типов с включённым контролем (или в GxP-режиме) при сохранении спрашивать причину изменения и писать её в контрольный след.

**P-6. Удаление полей шаблона → «архивирование поля»** [S1 ¶9]. Запрет удаления верен: данные терять нельзя. Но без выхода шаблоны со временем зарастут. Предлагаю «Архивировать»:
- поле исчезает из карточки и новых записей;
- данные и история остаются;
- поле можно вернуть.

Удаление разрешено, только пока нет ни одной КЕ типа (как в S1). Тип поля после появления данных менять нельзя.

**P-7. Связи:**
- **разрешённые пары типов** для типа связи [S2] — «Установлен на» имеет смысл между ПО и сервером, а не между сервером и договором;
- запрет связи КЕ с самой собой;
- контроль циклов для иерархических связей («Входит в»);
- **назначение веса 0–100** [S1 ¶16] нужно уточнить: для анализа влияния? для сортировки? (вопрос 15);
- что происходит со связями при выводе КЕ из эксплуатации: связи остаются, но помечаются.

**P-8. «Контролируемые даты».** Любое поле-дату в шаблоне можно отметить как отслеживаемое: окончание лицензии, гарантии, сертификата, поверки. Тогда работают уведомления за N дней и подсветка, как у мероприятий. Это закрывает [S2] (лицензии, гарантии) без отдельного кода.

**P-9. Мероприятия — дополнения к [S1 ¶11–14]:**
- интервал в **днях, неделях, месяцах, годах**: валидацию раз в 2 года удобнее задать «24 месяца», чем «730 дней»;
- отсчёт следующей даты — от фактической или от плановой (вопрос 9);
- **чек-лист работ** в мероприятии (то, что в [S2] названо «технологической картой») — при подтверждении все пункты отмечены;
- **вложения к подтверждению**: протокол, отчёт;
- **сквозной реестр и календарь мероприятий** по всем КЕ с фильтрами («мои», «просроченные», «на этой неделе») [S2];
- статусы мероприятия: «Запланировано», «Просрочено» (вычисляется), «Выполнено», «Отменено» (с причиной);
- **регулярные мероприятия по умолчанию из типа КЕ** [S1 ¶13]: изменение шаблона в типе не меняет уже созданные у КЕ мероприятия, но администратор может применить изменение массово.

**P-10. Матрица ответственности на КЕ** [S2]. «Роли ответственности» — это справочник: Владелец системы, Владелец процесса, ИТ-сопровождение, Бизнес-владелец; у каждой — основной и замещающий. Список ответственных типа КЕ [S1 ¶10] остаётся источником подсказок при выборе.

**P-11. Документы** [S1 ¶18], [S2]: файл или ссылка, **вид документа** (справочник), версия, дата, статус. Один документ можно связать с несколькими КЕ. Ссылки (база знаний, вики) можно вешать и на **тип КЕ**, не только на КЕ.

**P-12. Идентификация КЕ:**
- **уникальный Код** — ключ для API, импорта и интеграций [S2];
- проверка дублей при создании: тот же тип + совпадающее наименование или серийный номер — с предупреждением;
- **неизменяемый системный код поля** вместо переименуемых ID и алиасов [S1 ¶8]: при переименовании ломаются интеграции и правила. Отображаемое название поля менять можно, код — нет.

**P-13. Базовые поля карточки** (есть у всех типов, удалить нельзя [S1 ¶7]):
- Код, Наименование, Тип, Статус, Критичность, Местоположение, Описание;
- Ответственные (P-10);
- даты ввода и вывода из эксплуатации;
- служебные поля: кем и когда создана и изменена.

Окончательный список утверждает ВП.

**P-14. Общие справочники в ядре:** Местоположения (иерархия: площадка → здание → помещение), Организации (поставщики, производители, подрядчики), Контактные лица, Оргструктура (организации, подразделения), Сотрудники. Плюс **пользовательские справочники**: администратор создаёт свои списки значений для полей.

**P-15. Baseline** [S1 ¶17] (вопрос 10). По ITIL baseline — это **утверждённый снимок конфигурации, с которым сравнивают текущее состояние**. Предлагаю:
- версии baseline (v1, v2, …), каждая неизменяема;
- сравнение «текущее vs baseline» с подсветкой отличий;
- создание новой версии по отдельному праву, в GxP — с ЭП;
- окно «Сохранить как Baseline?» показывать только при первом сохранении КЕ, а не при каждом, если baseline отложили (иначе раздражает).

**P-16. Контрольный след: как обеспечить неизменяемость** [S1 ¶20]. Ответ на твой вопрос, детали спроектирует Архитектор:
- запись только добавлением, никаких функций изменения и удаления ни в интерфейсе, ни в API;
- на уровне БД у приложения нет прав UPDATE и DELETE на журнал, а триггеры отклоняют такие операции;
- **цепочка хэшей**: каждая запись содержит хэш предыдущей, поэтому любая правка «задним числом» (даже администратором БД) обнаруживается;
- встроенная **проверка целостности журнала** и периодическая выгрузка контрольной точки (хэша) во внешнее хранилище;
- время — с синхронизированного источника (NTP);
- просмотр журнала — по отдельному праву; экспорт для инспекции.

**P-17. Внешние обращения и инциденты** (Could). Ссылки из карточки на обращения во внешней ITSM-системе. Своим Service Desk не становимся.

**P-18. Импорт данных КЕ из Excel/CSV** — в описании нет, но без него заказчик не загрузит сотни существующих систем:
- скачивание шаблона по типу КЕ;
- сопоставление колонок;
- пробный прогон с отчётом об ошибках;
- обновление по Коду.

**P-19. Экспорт/импорт конфигурации** [S1 ¶4]. Предлагаю:
- **версионированный пакет** с манифестом и контрольной суммой;
- предварительный просмотр изменений перед применением (dry-run);
- режимы «в чистую систему» и «слияние с существующей» с правилами конфликтов;
- **секреты (токены ботов, пароли SMTP) в пакет не попадают** никогда;
- импорт пишется в контрольный след;
- в GxP изменение конфигурации валидированной системы — само по себе изменение, которое требует контроля.

**P-20. Мой Inbox для всех, а не только для согласующего** [S1 ¶23]: на согласование, к подписи, мои мероприятия на сегодня и неделю, просроченные. Колокольчик — для событий.

**P-21. Права — дополнения к [S1 ¶5–6]:**
- кроме CRUD, нужны отдельные права на действия: согласовать изменение, подписать, управлять baseline, экспортировать, смотреть контрольный след, настраивать типы, импортировать конфигурацию;
- правило «разрешение побеждает запрет» сохраняем;
- нужна роль **аудитора** только с правом чтения (инспектор, служба качества).

**P-22. QR-код на физической КЕ** (Could): наклейка → скан телефоном → карточка → подтвердить мероприятие на месте. Для этого карточка и подтверждение мероприятия должны нормально работать на телефоне. Остальной интерфейс рассчитан на компьютер.

**P-23. Качество данных** (Should): виджет и фильтры «КЕ с незаполненными обязательными полями» (после добавления нового обязательного поля [S1 ¶7]), «без ответственного», «без baseline», «возможные дубли».

**P-24. Аттестация данных** (Should, идея с рынка): владелец КЕ периодически подтверждает «карточка актуальна». В GxP это часть периодического пересмотра.

**P-25. Каналы уведомлений** [S1 ¶21]:
- SMTP достаточно для отправки, IMAP нужен только для приёма ответов, в v1 не нужен;
- в закрытом on-prem-контуре Telegram и MAX часто недоступны, поэтому в v1 предлагаю колокольчик, e-mail и **вебхук** — универсальный канал, через который подключаются корпоративные мессенджеры (eXpress, VK Teams, Пачка, Битрикс24, Mattermost); Telegram и MAX — следующей очередью (вопрос 11);
- привязка Telegram требует отдельного сценария: пользователь пишет боту код из профиля;
- журнал доставки с повторами виден администратору.

### 5.2 Где KE может выделиться
1. **ЭП по 21 CFR Part 11 и неизменяемый контрольный след с проверкой целостности.** Среди российских CMDB таких не нашлось (не подтверждено, что их нет совсем).
2. **Плановые мероприятия как ядро плюс GxP-пакет.** Российские CMDB построены вокруг ITSM/ITAM, а специализированные системы валидации — дорогие и зарубежные. Ниша: «реестр компьютеризированных систем и их жизненного цикла» для российской фармы, с той же коробкой для обычной IT-службы.
3. **Перенос конфигурации пакетами.** Из российских продуктов это есть только у SimpleOne, и там это возможность платформы, а не прикладной коробки.

### 5.3 Новые предложения по итогам обзора
- **P-26.** Владельцы КЕ, на которые влияет изменяемая КЕ, автоматически добавляются в согласующие (Should, после v1).
- **P-27.** В GxP-пакете переход в статус «Валидирована» возможен только при наличии обязательных документов (URS, оценка рисков, IQ/OQ/PQ, отчёт о валидации) и выполненных мероприятий. Это частный случай условий перехода из P-1.
- **P-28.** «Устаревшие КЕ» — не изменялись и не подтверждались N дней (настройка) — показатель качества данных (дополнение к P-23).
- **P-29.** У пункта чек-листа мероприятия есть признак «обязательный» и тип ответа: отметка, значение (число с единицей и допуском), файл или фото (дополнение к P-9).
- **P-30.** Правила согласования: в v1 — «любой участник роли»; позже — «все» и «большинство».
- **P-31.** Проверка конфликтов изменения с окнами обслуживания и с затронутыми КЕ (Could, после v1).

### 5.4 Виджеты главной страницы v1 (предложение к F-18)
Каждый виджет — счётчик со ссылкой на отфильтрованный реестр.
- КЕ по типам и статусам.
- Требуют внимания:
  - просроченные мероприятия;
  - мероприятия на ближайшие N дней;
  - контролируемые даты, истекающие через 30/60/90 дней.
- Мои дела: на согласование, к подписи, мои мероприятия.
- Качество данных: % заполненности обязательных полей, КЕ без ответственного, без baseline, устаревшие, возможные дубли.
- При включённом GxP-пакете: распределение по статусам валидации, просроченные периодические пересмотры.

Графические и настраиваемые дашборды — следующей очередью, когда накопятся данные о том, что смотрят пользователи [S1 ¶25].

### 5.5 GxP-пакет: карточка компьютеризированной системы (черновик)
Источники: Annex 11 §4.3; Рекомендация Коллегии ЕЭК № 25 (2023): наименование, версия, поставщик, владелец, местоположение, назначение, риск; ГОСТ Р 57680-2017 добавляет статус валидации; GAMP 5; PIC/S PI 041-1. Списки значений — частично отраслевая практика, а не текст норм. В 2025 году опубликован проект новой редакции Annex 11; на октябрь 2026 он не окончательный, поэтому отслеживаем его.

| Статус валидации | не оценивалась / не требуется / запланирована / в процессе / валидирована / валидирована с ограничениями / требуется ревалидация / выведена |

## 7. Вопросы к ВП (раунд 1)

### 7.0 Решения ВП по раунду 1 [PO 2026-10-08]

| № | Решение | Что это значит для требований |
|---|---|---|
| 1 | **a** — Категория → Тип | Категория задаёт общие поля, мероприятия и статусную модель; тип добавляет свои поля |
| 2 | **a** — настраиваемая статусная модель | Статусы, переходы, права на переход, условия, ЭП — на уровне категории |
| 3 | **a** — согласуются только контролируемые поля и переходы | Флаг «контролируемое» в шаблоне поля и в переходе статуса |
| 4 | **a** + уточнение ВП | Роль с одним или несколькими участниками; автор не согласует своё изменение; замещение. **Когда один участник согласовал, задания у остальных теряют силу:** они получают уведомление, что согласование уже не нужно, а попытка отказать или согласовать повторно отклоняется с сообщением «Запрос уже согласован». Уточнение для случая отказа — R2-1 |
| 5 | **a** — ЭП по Part 11 / Annex 11 в v1 | Повторный ввод пароля и значение подписи; УНЭП/КЭП (КриптоПро) — опция позже |
| 6 | **a** — только мягкое удаление | Окончательная очистка — администратором и только без GxP-режима |

### 7.1 Вопросы раунда 1 (как были заданы)

Отвечать можно в формате «1a, 2b…». Рекомендованный вариант стоит первым.

1. **Классификация типов КЕ.**
   - a) Два уровня: **Категория** (общие поля, мероприятия и статусная модель, например «Компьютеризированная система» с GxP-полями) → **Тип** (добавляет свои поля). Так в [S2]. **(рекомендую)**
   - b) Дерево любой глубины с наследованием полей: гибче, но сложнее для администраторов.
   - c) Плоский список типов; общие поля переносятся копированием шаблона.
2. **Жизненный цикл КЕ** (P-1).
   - a) Настраиваемая статусная модель на категорию: статусы, разрешённые переходы, кто переводит, условия, ЭП. **(рекомендую)**
   - b) Один фиксированный набор статусов для всех типов.
   - c) Статус — просто поле-список без правил.
3. **Что требует согласования при включённом контроле изменений** (P-3).
   - a) Поля, отмеченные в шаблоне как «контролируемые», и отмеченные переходы статуса; остальное сохраняется сразу. **(рекомендую)**
   - b) Все изменения карточки, как в описании.
4. **Согласующий** (P-2).
   - a) Роль с одним или несколькими участниками: согласует любой из них, автор не может согласовать своё изменение, есть замещение. **(рекомендую)**
   - b) Ровно один участник, как в описании.
5. **Электронная подпись.**
   - a) В v1 — электронная подпись по 21 CFR Part 11 / Annex 11: повторный ввод пароля и «значение подписи» («Утверждаю», «Выполнено», «Проверено»); УНЭП/КЭП через КриптоПро — позже, как опция. **(рекомендую)**
   - b) Сразу УНЭП/КЭП через КриптоПро: нужны сертификаты и плагин у каждого пользователя.
   - c) Только простая подпись, без требований Part 11.
6. **Удаление КЕ.**
   - a) Физического удаления нет. «Удалить» — мягкое удаление: КЕ скрыта, её можно восстановить, история сохраняется. Окончательная очистка — только администратором и только вне GxP-режима. **(рекомендую)**
   - b) Физическое удаление по праву Delete, как в описании.
   - c) Удаления нет вообще, только вывод из эксплуатации.
7. **Ответственные — это пользователи или сотрудники?**
   - a) Отдельный справочник **Сотрудников** (из AD или 1С:ЗУП, с подразделениями). Учётные записи есть только у тех, кто входит в систему. Ответственным может быть любой сотрудник, а подтверждать мероприятия — только пользователь. **(рекомендую)**
   - b) Только пользователи системы.
8. **Ограничение доступа к записям** [S2].
   - a) Роль + типы КЕ (как в описании) + у роли опция «только КЕ моего подразделения / где я ответственный». **(рекомендую)**
   - b) Только роль + типы КЕ.
9. **Дата следующего регулярного мероприятия.**
   - a) Интервал в днях, неделях, месяцах или годах. Отсчёт настраивается в мероприятии: от фактической даты выполнения или от плановой. **(рекомендую)**
   - b) Только дни и только от фактической даты, как в описании.
10. **Baseline** (P-15).
    - a) Неизменяемые версии с номерами, сравнение «текущее vs baseline», новая версия — по отдельному праву и с ЭП в GxP. **(рекомендую)**
    - b) Один baseline, который перезаписывается; история изменений — в контрольном следе.
11. **Каналы уведомлений и таск-трекеры в v1.**
    - a) Колокольчик, e-mail, вебхук. Задачи в Яндекс Трекер и Jira с отображением статуса задачи. Выполнение мероприятия подтверждается только в KE, закрытие задачи его не закрывает. Telegram и MAX — следующей очередью. **(рекомендую)**
    - b) То же, но Telegram и MAX сразу в v1.
    - c) То же, но закрытие задачи в трекере автоматически подтверждает выполнение (без ЭП).
12. **Пакеты конфигурации в поставке.**
    - a) Поставлять «Базовый ИТ-пакет» (серверы, ПО, сети, рабочие места) и «GxP-пакет» (компьютеризированные системы, оборудование, GxP-поля и мероприятия, ЭП, контроль изменений, §3). **(рекомендую)**
    - b) Только пустая система; настройку делает заказчик или внедренец.
13. **ЗИП, поставщики, технические работы из [S2].**
    - a) Без отдельных модулей. ЗИП — настраиваемый тип КЕ, поставщики — справочник Организаций с контактами на КЕ, техкарта — шаблон регулярных мероприятий с чек-листом, работы исполняются в таск-трекере. **(рекомендую)**

14. **Целевой масштаб одной установки** — для требований к производительности.
    - a) До 50 000 КЕ, до 200 000 связей, до 1 000 пользователей, до 100 одновременно работающих. **(рекомендую как ориентир v1)**

15. **Короткие уточнения:**

    - b) Языки интерфейса: только русский, или русский и английский (для международных фармкомпаний)?

### 7.2 Вопросы раунда 2 (уточнения по ответам)

R2-1. **Отказ при нескольких согласующих.**
- a) Первое решение окончательное — и «согласовано», и «отказано». Остальные получают уведомление «решение принято: <кто>, <что>», их задания закрываются. **(рекомендую: симметрично и предсказуемо)**
- b) Отказ одного участника не окончательный: запрос ждёт, пока кто-то не согласует или пока не откажут все.

R2-2. **Как разделять данные нескольких юрлиц.**
- a) Организация — измерение данных. У каждой КЕ есть организация-владелец; роль ограничивается организациями, как подразделениями в ответе 8a. Конфигурация (категории, типы, поля, справочники) общая на всю установку. КЕ может быть **общей** для нескольких организаций (общий ЦОД холдинга). Связи между КЕ разных организаций разрешены. **(рекомендую: так устроены холдинги)**
- b) Полная изоляция: у каждой организации своя конфигурация, справочники и пользователи, данные не пересекаются — по сути несколько систем в одной установке.
- c) Как a, но организация может добавлять свои типы и справочники поверх общих.

R2-3. **Обязательные серверные ОС.**
- a) Windows Server и российские Linux: Astra Linux SE, РЕД ОС, Альт. **(рекомендую: так обычно требуют компании с импортозамещением; эти ОС проверяем в CI или на стендах)**
- b) Windows Server и «любой распространённый Linux», без отдельной проверки российских ОС.

R2-4. **СУБД.**
- a) Только PostgreSQL-совместимые: PostgreSQL и Postgres Pro. **(рекомендую: подходит для реестра, бесплатно, одна СУБД вдвое дешевле в разработке и тестировании)**
- b) Плюс MS SQL Server.
- c) Плюс Oracle.

R2-5. **Целевое время отклика** при объёмах из ответа 14b, на сервере из минимальных требований.
- a) **(рекомендую)**:
  - открытие карточки КЕ и страница реестра — не более 1 с для 95% запросов;
  - поиск и фильтр по реестру — не более 2 с;
  - экспорт 100 000 строк — не более 1 мин;
  - анализ влияния до глубины 5 — не более 3 с.
- b) Свои цифры.

R2-6. **Смысл веса связи.** Сейчас в описании: «отсутствие веса = 0» [S1 ¶16].
- a) Вес — **сила зависимости**: 0 — отказ одной КЕ не влияет на другую, 100 — полностью зависит. Влияние по цепочке — произведение весов; КЕ ниже порога (по умолчанию 10%) не показываются. **Связь без веса считается 100**, иначе связи, заведённые без веса, тихо выпадут из анализа. Результат — список затронутых КЕ с итоговым процентом и критичностью. **(рекомендую)**
- b) Вес — просто атрибут для фильтра и сортировки, без расчёта.
- c) Как a, но связь без веса = 0, как в описании: такие связи в анализ влияния не попадают.

## 8. Допущения
- **A-1.** Пользователи работают на компьютере в браузере; на телефоне нужны только просмотр карточки и подтверждение мероприятия (P-22).
- **A-2.** Система не заменяет Service Desk и таск-трекер: работы исполняются там, а KE хранит план, факт и подтверждение.
- **A-3.** Пароли и секреты от самих КЕ (учётки серверов и т.п.) в KE не хранятся.
- **A-4.** Локализация (решение 15b) в v1 касается текстов интерфейса. Названия категорий, типов, статусов и других записей справочников пока хранятся на одном языке; перевод справочных данных — по отдельному решению.
- **A-5.** Реестр российского ПО (решение 15d): все компоненты продукта — российские или open-source, без обязательной зависимости от зарубежных облачных сервисов. Интеграции с зарубежными системами (Jira, Telegram) — опциональные коннекторы.
