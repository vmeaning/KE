# F-01. Категории и типы КЕ, конструктор карточек

> Статус: draft · 2026-10-10 · Приоритет: Must
> Источник: S1 ¶6–10, ¶13; S2; R1a (Категория → Тип); P-6, P-8, P-12, P-13; domain-model §3.1–3.4; INV-1…INV-7
> Зависит от: F-19 · Связано: F-02 (карточка по шаблону), F-03 (статусная модель категории), F-05 (шаблоны мероприятий), F-08 (контроль изменений, регулируемая категория), F-10 (документы и ссылки на типе), F-13 (права на новый тип) · Экраны: появятся у дизайнера

## 1. Цель
Администратор конфигурации без программиста описывает, какие КЕ учитываются и какие данные о них хранятся. Он может менять это и тогда, когда КЕ уже есть, не ломая данные. Фича решает задачу, если:
- новая категория с типом и полями настроена без участия поставщика и открыта ролям;
- после добавления обязательного поля существующие КЕ открываются и работают (INV-6).

## 2. Роли и права
Права по умолчанию (README §5, строка «Настройка категорий, типов, полей…»).

| Роль | Видит | Создаёт и меняет | Деактивирует и удаляет |
|---|---|---|---|
| Администратор системы, администратор конфигурации | настройки всех категорий и типов | категории, типы, поля, шаблоны карточек | по правилам BR4, BR9, BR10, BR27, BR28 |
| Остальные роли | — (результат видят в карточках КЕ) | — | — |

Права ролей на КЕ нового типа даёт администратор системы (F-13).

## 3. User stories
- **F-01.US1** — Как администратор конфигурации, я хочу создать категорию КЕ с общими полями, чтобы не повторять одни и те же поля в каждом типе.
- **F-01.US2** — Как администратор конфигурации, я хочу создать тип КЕ внутри категории со своими полями, чтобы учитывать специфику, например «ЛИМС» и «SCADA».
- **F-01.US3** — Как администратор конфигурации, я хочу добавлять поля разных типов данных с проверками, значениями по умолчанию и подсказками, чтобы пользователи вводили корректные данные.
- **F-01.US4** — Как администратор конфигурации, я хочу расставить поля по группам, разделителям и текстовым блокам, чтобы карточка была понятной.
- **F-01.US5** — Как администратор конфигурации, я хочу добавлять поля и делать их обязательными, когда КЕ уже есть, чтобы развивать учёт, не ломая существующие КЕ.
- **F-01.US6** — Как администратор конфигурации, я хочу архивировать ненужное поле, чтобы убрать его из карточки, не теряя данных и истории.
- **F-01.US7** — Как администратор конфигурации, я хочу отметить поле-дату как контролируемую, чтобы ответственные получали уведомления об окончании лицензии, гарантии или поверки.
- **F-01.US8** — Как администратор конфигурации, я хочу задать в типе список ответственных-подсказок и при необходимости ограничить выбор только ими, чтобы мероприятия назначались нужным людям [S1 ¶10].
- **F-01.US9** — Как администратор конфигурации, я хочу настроить новый тип незаметно для пользователей, чтобы открыть его ролям, только когда он готов [S1 ¶6].
- **F-01.US10** — Как администратор конфигурации, я хочу деактивировать тип, который больше не используется, чтобы по нему не создавали новые КЕ.
- **F-01.US11** — Как администратор конфигурации, я хочу задать в типе шаблон кода КЕ, чтобы коды новых КЕ присваивались автоматически и единообразно. [вопрос 2]
- **F-01.US12** — Как администратор конфигурации, я хочу копировать тип и видеть предпросмотр карточки, чтобы быстрее настраивать похожие типы. [вопрос 9]

## 4. Бизнес-правила

**Категории**
- **F-01.BR1** — КЕ классифицируется в два уровня: категория → тип [R1a]. У каждой КЕ ровно один тип, у каждого типа — ровно одна категория.
- **F-01.BR2** — Атрибуты категории [domain-model §3.1]:
  - код — не меняется [INV-1], формат — INV-24;
  - название — обязательно, уникально среди категорий;
  - описание;
  - иконка — из встроенного набора.

  Название, описание и иконку можно менять в любой момент.
- **F-01.BR3** — Категория задаёт для всех своих типов:
  - настраиваемые поля категории;
  - статусную модель (F-03);
  - шаблоны мероприятий (F-05);
  - контроль изменений и признак «Регулируемая» (F-08, BR35);
  - документы и ссылки (F-10).
- **F-01.BR4** — Категорию можно удалить, только если в ней нет типов. Вместе с ней удаляются её поля, статусная модель и шаблоны мероприятий. [PROPOSAL]
- **F-01.BR5** — Новая категория получает статусную модель одним из двух способов, по выбору администратора: [PROPOSAL]
  - копия модели другой категории;
  - модель из одного статуса «В эксплуатации» — начального и эксплуатационного.

**Типы**
- **F-01.BR6** — Атрибуты типа [domain-model §3.2]:
  - категория — обязательна;
  - код — не меняется [INV-1], уникален среди типов всей установки, формат — INV-24;
  - название — обязательно, уникально внутри категории;
  - описание;
  - иконка — если не задана, используется иконка категории;
  - «действует».
- **F-01.BR7** — Категорию типа можно сменить, пока у типа нет ни одной КЕ, в том числе мягко удалённой [domain-model §3.2].
- **F-01.BR8** — Новый тип создаётся так [S1 ¶6–7, INV-7]:
  - шаблон карточки по умолчанию — базовые поля и поля категории;
  - права всех ролей, кроме роли «Администратор системы», пустые.

  Поэтому тип не виден пользователям, пока администратор системы не даст ролям права (F-13). Пример: администратор конфигурации создаёт тип «СХД» и настраивает поля. Администратор системы заводит тестовую КЕ. Инженеры увидят тип, только когда их роль получит право Read.
- **F-01.BR9** — Тип нельзя сделать недействующим, пока у него есть КЕ не в конечных статусах [S2, domain-model §3.2]. Мягко удалённые КЕ не мешают [PROPOSAL]. Недействующий тип:
  - нельзя выбрать для новых КЕ;
  - не мешает работать с существующими КЕ этого типа;
  - не мешает восстановить мягко удалённую КЕ этого типа: она остаётся КЕ недействующего типа [PROPOSAL];
  - можно снова сделать действующим.
- **F-01.BR10** — Тип можно удалить, только если у него нет КЕ, в том числе мягко удалённых. Если на тип ссылаются допустимые пары типов связей (F-04.BR4), удалить его нельзя, пока ссылки не убраны; система перечисляет эти типы связей. Вместе с типом удаляются его поля, шаблон карточки, шаблоны мероприятий и права ролей на него. [PROPOSAL]
- **F-01.BR11** — Ответственные типа [S1 ¶10, domain-model §3.2]: список сотрудников-подсказок и флажок «Только указанные ответственные». Правило выбора одинаково для матрицы ответственности КЕ (F-02) и ответственного за мероприятие (F-05):
  - список пуст — доступен поиск по всем работающим сотрудникам;
  - список задан, флажок снят — сначала предлагаются сотрудники из списка, затем доступен поиск по всем;
  - флажок установлен — выбрать можно только сотрудников из списка, поиска нет.

  Изменение списка или флажка не меняет уже назначенных ответственных. Пример: у типа «SCADA» в списке Петров и Сидоров, флажок установлен. Назначить Иванова ответственным за КЕ «SCADA цеха 3» нельзя. [PROPOSAL: правило действует и для матрицы ответственности]
- **F-01.BR12** — Шаблон кода КЕ в типе — префикс и число цифр порядкового номера [вопрос 2]:
  - пример: префикс «SRV-», 6 цифр → «SRV-000124»;
  - счётчик общий для одинакового префикса во всей установке и пропускает уже занятые коды;
  - если шаблона нет, код КЕ вводят вручную.

  Как код используется при создании КЕ — F-02.BR21.
- **F-01.BR13** — Копирование типа [вопрос 9]:
  - новый тип создаётся в той же категории;
  - копируются поля типа, шаблон карточки, ответственные типа и шаблоны мероприятий типа;
  - код и название задаются заново;
  - права ролей на новый тип пустые [INV-7].

**Поля**
- **F-01.BR14** — Базовые поля есть у каждой КЕ, удалить их нельзя [INV-2, P-13]:
  - Код, Наименование, Тип, Статус, Критичность;
  - Организация-владелец, Общая для организаций, Подразделение-владелец [вопрос 4];
  - Местоположение, Описание, Ответственные;
  - Дата ввода в эксплуатацию, Дата вывода из эксплуатации;
  - служебные: создана (кем, когда), изменена (кем, когда), дата последнего подтверждения актуальности.

  Обязательны всегда: Код, Наименование, Тип, Статус, Критичность, Организация-владелец. Местоположение, Описание, Подразделение-владелец и Ответственные можно сделать обязательными в категории или типе [S1 ¶7; PROPOSAL]. Обязательность Ответственных означает: в матрице есть хотя бы одна строка.
- **F-01.BR15** — Настраиваемое поле администратор добавляет в категорию или в тип [S1 ¶7]. Поле категории наследуют все её типы. У типа — не больше 200 настраиваемых полей вместе с полями категории. [PROPOSAL: 200]
- **F-01.BR16** — Код поля [INV-1, P-12]:
  - формат — латиница по INV-24;
  - система предлагает код из названия транслитерацией;
  - после сохранения поля код не меняется;
  - код уникален в пределах категории вместе со всеми её типами;
  - код не совпадает с кодами базовых полей.

  Пример: в категории «Компьютеризированная система» есть поле `gamp_category`. Тип «ЛИМС» не может добавить своё поле с этим кодом.
- **F-01.BR17** — Название поля обязательно и уникально среди полей одной карточки: базовых, полей категории и полей типа. Название и подсказку можно менять в любой момент. Подсказка — до 500 символов, показывается рядом с полем. [PROPOSAL: уникальность названия, длина подсказки]
- **F-01.BR18** — Типы данных и их параметры [domain-model §3.3]:

  | Тип данных | Параметры и проверка |
  |---|---|
  | Строка | одна строка до 255 символов; проверка — маска (регулярное выражение) с текстом ошибки, который задаёт администратор, или готовый формат: IPv4, IPv6, MAC-адрес, имя хоста [вопрос 9] |
  | Текст | многострочный, до 10 000 символов, без форматирования |
  | Число | точность — 0–6 знаков после запятой (0 — целое); единица измерения; минимум; максимум |
  | Дата | минимум; максимум; флажок «не позже текущей даты» |
  | Дата-время | хранится в UTC, показывается в часовом поясе пользователя (NFR-11) |
  | Флаг | «да» или «нет»; пустого значения нет; по умолчанию «нет»; признак «обязательное» не применяется |
  | Значение справочника | простой справочник (F-19); одна или несколько записей; в иерархическом справочнике запись выбирают из дерева |
  | Сотрудник | один работающий сотрудник; ответственные типа (BR11) это поле не ограничивают |
  | Контрагент | один действующий контрагент |
  | Местоположение | запись справочника «Местоположения», выбор из дерева |
  | URL | начинается с `http://` или `https://` |
  | E-mail | проверка формата |
  | Телефон | по domain-model §3.3: проверка при вводе, приведение российских номеров к «+7», группировка цифр |

  [PROPOSAL: длины, точность, готовые форматы строк]
- **F-01.BR19** — Тип данных поля не меняется, если поле заполнено хотя бы у одной КЕ, в том числе мягко удалённой [INV-5]. При попытке система объясняет причину: «Тип данных нельзя изменить: поле заполнено у 37 КЕ». Пока данных нет, тип данных менять можно.
- **F-01.BR20** — Параметры проверки можно менять и при наличии данных: маску, диапазон, точность, максимальную длину. Уже сохранённые значения, которые не соответствуют новым правилам, остаются и подсвечиваются в карточке. Такое значение не мешает сохранить КЕ, если поле не меняли. Новое значение поля должно соответствовать новым правилам. [PROPOSAL]
- **F-01.BR21** — Обязательность поля можно включить в любой момент [INV-6, S1 ¶7]:
  - существующие КЕ с пустым полем становятся неполными и продолжают работать;
  - при следующем сохранении карточки в интерфейсе нужно заполнить поле (F-02.BR25);
  - частичное обновление КЕ через API или импорт не блокируется пустым обязательным полем;
  - при создании КЕ любым способом обязательные поля нужно заполнить; исключение — поля «только для чтения в интерфейсе» при создании в интерфейсе (BR24).

  Пример: в тип «Сервер» с 1 200 КЕ добавили обязательное поле «Инвентарный номер». Все 1 200 КЕ стали неполными, и ни одна не перестала открываться. [PROPOSAL: правило для API и импорта]
- **F-01.BR22** — Значение по умолчанию подставляется только в новые КЕ. У существующих КЕ новое поле пустое, флаг — «нет».
- **F-01.BR23** — Признак «Уникальное в типе» есть у строки, числа, URL и e-mail [вопрос 3]:
  - КЕ не сохранится, если значение этого поля совпадает со значением у другой КЕ того же типа, в том числе мягко удалённой;
  - запрет действует в интерфейсе, через API и при импорте;
  - строки сравниваются без учёта регистра и пробелов по краям;
  - пустые значения не сравниваются;
  - сообщение называет КЕ, у которой уже есть такое значение, если пользователь её видит;
  - признак нельзя включить, пока у КЕ типа есть повторяющиеся значения; система их показывает.

  Пример: у сервера SRV-000012 серийный номер «CZ1234». Второй сервер с серийным номером «cz1234» не сохранится.
- **F-01.BR24** — Поле «Только для чтения в интерфейсе» видно в карточке всем, но не редактируется никем, включая администратора. Значение меняют только API (F-15) и импорт (F-16) [domain-model §3.3]. Если такое поле обязательное и пустое, КЕ неполная, но это не мешает создать и сохранить её в интерфейсе: обязательность такого поля проверяют только API и импорт при создании КЕ. [PROPOSAL]
- **F-01.BR25** — Флажок «Контролируемое» есть у настраиваемых полей. Он действует, когда в категории включён контроль изменений (F-08) [P-3]. Базовые поля, кроме Статуса и служебных, можно отметить контролируемыми в настройках категории. Статус контролируется через переходы (F-03.BR16). [PROPOSAL: контролируемые базовые поля]
- **F-01.BR26** — Контролируемая дата — только для полей-дат [P-8]:
  - до трёх сроков уведомления — за сколько дней до даты;
  - получатели — роли ответственности из матрицы КЕ;
  - каналы — из настроенных (F-06).

  Пример: «Дата окончания лицензии» — за 90, 30 и 7 дней владельцу системы по e-mail и в колокольчик. Подсветка — как у мероприятий (F-02.BR11). Уведомления и подсветка работают только у КЕ в эксплуатационных статусах, не удалённых. [PROPOSAL: получатели, подсветка]
- **F-01.BR27** — Архивировать можно любое настраиваемое поле [P-6]. Архивированное поле:
  - не показывается в карточке и не заполняется;
  - недоступно в новых фильтрах и колонках;
  - не делает КЕ неполной.

  Значения сохраняются и видны в истории КЕ. Поле можно вернуть из архива вместе со значениями. Сохранённые представления, где было это поле, работают без него.
- **F-01.BR28** — Настраиваемое поле можно удалить, только пока нет ни одной КЕ, в том числе мягко удалённой [INV-3, S1 ¶9]:
  - для поля категории — ни одной КЕ этой категории;
  - для поля типа — ни одной КЕ этого типа.

  Иначе поле можно только архивировать.
- **F-01.BR29** — Если у категории или типа уже есть КЕ, система предупреждает [INV-3, S1 ¶9]:
  - при открытии шаблона карточки на редактирование: «У типа есть КЕ. Добавленные поля нельзя будет удалить — только архивировать»;
  - при попытке удалить настраиваемое поле: «Поле нельзя удалить: у типа есть КЕ. Архивировать?».

  Правила флажка «Больше не предупреждать»:
  - он есть у каждого предупреждения и действует только для этого пользователя;
  - вернуть отключённые предупреждения можно в профиле [PROPOSAL];
  - если отключено второе предупреждение, у поля вместо действия «Удалить» доступно «Архивировать» [PROPOSAL].

**Шаблон карточки**
- **F-01.BR30** — Шаблон карточки задаётся для типа [S1 ¶7, domain-model §3.2, §3.4]. В нём порядок полей — базовых, категории и типа — и элементы оформления:
  - группа полей — заголовок, можно сворачивать, флажок «свёрнута по умолчанию» [PROPOSAL: флажок];
  - разделитель;
  - текстовый блок — до 1 000 символов [PROPOSAL: длина].
- **F-01.BR31** — Элементы оформления добавляются и удаляются в любой момент, в том числе когда у типа есть КЕ [INV-4, S1 ¶9].
- **F-01.BR32** — Новое поле категории появляется в конце шаблонов всех её типов. Администратор переставляет его в каждом типе отдельно. [PROPOSAL]
- **F-01.BR33** — Дополнительные возможности конструктора [вопрос 9]:
  - ширина поля в шаблоне — вся строка или половина;
  - предпросмотр: карточка выглядит так, как её увидит пользователь.
- **F-01.BR34** — Изменения категорий, типов, полей и шаблонов пишутся в контрольный след как изменение конфигурации: кто, когда, что было, что стало (F-11).

**Регулируемая категория**
- **F-01.BR35** — Признак категории «Регулируемая» [глоссарий, P-5, R6a] включает два правила для всех КЕ категории:
  - обязательная причина изменения (F-08);
  - запрет очистки (F-03.BR27, INV-18).

  Признак можно включить в любой момент. При выключении нужно указать причину, выключение пишется в контрольный след. КЕ, которые были в категории, пока она была регулируемой, очистить нельзя и после выключения (F-03.BR27, INV-18). [PROPOSAL: правило выключения]

## 5. Сценарии приёмки
Пишутся при подготовке ТЗ фазы, в которую войдёт фича (допущение A-9).

## 7. Интерфейс (для дизайнера)
- **Раздел администрирования «Категории и типы».** Дерево: категории, внутри — типы. Поиск, признак «недействующий».
- **Карточка категории.** Разделы:
  - общие сведения;
  - поля категории;
  - статусная модель (F-03);
  - шаблоны мероприятий (F-05);
  - контроль изменений и «Регулируемая» (F-08);
  - документы и ссылки (F-10).
- **Карточка типа.** Разделы:
  - общие сведения, включая шаблон кода;
  - поля типа;
  - конструктор шаблона карточки;
  - ответственные типа;
  - шаблоны мероприятий (F-05);
  - документы и ссылки (F-10).

  Действия: «Копировать тип», «Сделать недействующим», «Удалить».
- **Конструктор шаблона карточки.**
  - Палитра: поля, группа, разделитель, текстовый блок.
  - Элементы расставляются перетаскиванием.
  - Панель свойств выбранного поля.
  - Предпросмотр.
  - Базовые поля помечены и не удаляются.
  - Предупреждения BR29 с флажком «Больше не предупреждать».
- **Свойства поля.** Набор параметров зависит от типа данных (BR18). Сообщения:
  - почему тип данных нельзя изменить (BR19);
  - почему поле нельзя удалить (BR28).
- **Профиль пользователя.** Действие «Вернуть отключённые предупреждения».

## 8. Не входит
- Дерево классификации глубже двух уровней (R1a).
- Общие поля для нескольких категорий.
- Перенос поля из типа в категорию и обратно.
- Условная видимость полей: поле показывается только при определённом значении другого поля. Позже, если ВП не выберет вариант 9b.
- Права на уровне отдельных полей: скрыть поле от роли.
- Вычисляемые поля и формулы.
- Многоязычные названия полей (A-4).
