# F-03. Статусная модель и жизненный цикл КЕ

> Статус: approved · 2026-10-14 · Приоритет: Must
> Источник: R2a, R6a; P-1, P-27; OQ-4; [PO 2026-10-09] (очистка выключена по умолчанию); domain-model §3.5, §4.1, §9.1; INV-16…INV-18; README §5
> Зависит от: F-01 · Связано: F-02 (действия в карточке и реестре), F-05 (мероприятия считаются по эксплуатационным статусам), F-08 (контролируемые переходы, причина изменения), F-10 (условия по документам), F-12 (ЭП на переходе), F-15 и F-16 (статус при создании через API и импорт) · Экраны: появятся у дизайнера

## 1. Цель
Жизненный цикл КЕ описан явно, и система его соблюдает: КЕ проходит только разрешённые переходы, при выполненных условиях, с подписью и согласованием там, где они требуются. Фича решает задачу, если:
- КЕ GxP-пакета нельзя ввести в эксплуатацию без действующих документов валидации и нужного статуса валидации;
- ошибочно созданную КЕ можно убрать и восстановить, не потеряв историю.

## 2. Роли и права
Права по умолчанию (README §5). Право выполнять переход дополнительно ограничено ролями перехода (BR10).

| Роль | Видит статус КЕ | Настраивает модель | Выполняет переходы | Мягкое удаление и восстановление | Очистка |
|---|---|---|---|---|---|
| Администратор системы | ✓ | ✓ | ✓ | ✓ | ✓, если разрешена, только в нерегулируемых категориях |
| Администратор конфигурации | ✓ | ✓ | — | — | — |
| Менеджер конфигураций | ✓ | — | ✓ | ✓ | — |
| Инженер | ✓ | — | ✓ | — | — |
| Согласующий, Аудитор, Наблюдатель | ✓ | — | — | — | — |

История переходов видна в истории КЕ — по праву «Просмотр истории КЕ» (F-11).

## 3. User stories
Роли настраиваются (README §5), поэтому story называет право, а не роль. Какие роли получают право по умолчанию — таблица §2 [ревью ВП 2026-10-14].

- **F-03.US1** — Как пользователь с правом настройки конфигурации, я хочу настроить статусную модель категории — статусы, их признаки и переходы, — чтобы жизненный цикл КЕ отражал процессы заказчика.
- **F-03.US2** — Как пользователь с правом настройки конфигурации, я хочу задать условия перехода — заполненные поля, нужные значения, выполненные мероприятия, действующие документы, — чтобы КЕ нельзя было, например, ввести в эксплуатацию без валидации.
- **F-03.US3** — Как пользователь с правом настройки конфигурации, я хочу указать, какие роли выполняют переход и нужны ли для него ЭП и согласование, чтобы ключевые переходы были под контролем.
- **F-03.US4** — Как пользователь с правом Update на тип КЕ, которому разрешён переход, я хочу перевести КЕ в другой статус и сразу видеть, каких условий не хватает, чтобы понимать, что ещё нужно сделать.
- **F-03.US5** — Как пользователь с правом Delete на тип КЕ, я хочу мягко удалить ошибочно созданную КЕ с указанием причины и при необходимости восстановить её, чтобы реестр был чистым, а история сохранялась.
- **F-03.US6** — Как пользователь с правом «Очистка удалённых КЕ», я хочу окончательно очистить мягко удалённые КЕ нерегулируемых категорий, если очистка разрешена в настройках системы, чтобы избавиться от мусора. Очистка фиксируется в контрольном следе (BR29) [ревью ВП 2026-10-14].
- **F-03.US7** — Как пользователь с правом «Просмотр истории КЕ», я хочу видеть в истории КЕ все переходы — кто, когда, откуда, куда, причина, подпись, — чтобы подтвердить инспектору, что жизненный цикл соблюдался.

## 4. Бизнес-правила

**Статусная модель**
- **F-03.BR1** — У каждой категории своя статусная модель, её используют все типы категории [R2a, domain-model §3.5]. Модель новой категории — F-01.BR5.
- **F-03.BR2** — Атрибуты статуса:
  - код — не меняется [INV-1], формат — INV-24;
  - название — обязательно, уникально в модели;
  - цвет — из палитры дизайн-системы;
  - порядок показа;
  - признаки: начальный, эксплуатационный, конечный.
- **F-03.BR3** — В модели ровно один начальный статус [domain-model §3.5]. Запрещённые сочетания признаков:
  - эксплуатационный и конечный одновременно;
  - начальный и конечный одновременно.
- **F-03.BR4** — Что дают признаки статуса [domain-model §3.5, §9.2]:
  - **начальный** — его получает новая КЕ, созданная в интерфейсе;
  - **эксплуатационный** — по КЕ в таком статусе считается статус срока мероприятий и контролируемых дат и уходят уведомления о сроках (F-05, F-06);
  - **конечный** — жизненный цикл КЕ завершён; тип можно сделать недействующим, только когда все его КЕ, кроме мягко удалённых, в конечных статусах (F-01.BR9).
- **F-03.BR5** — Изменение признаков сразу действует на все КЕ в этом статусе. Пример: статус «На обслуживании» сделали неэксплуатационным, и по КЕ в нём сразу перестали приходить уведомления о сроках.
- **F-03.BR6** — Статус можно добавить в любой момент. Удалить статус можно, только если:
  - в нём нет ни одной КЕ, в том числе мягко удалённой;
  - на переход в него не ссылается активный запрос на изменение.

  Переходы из удалённого статуса и в него удаляются вместе с ним.
- **F-03.BR7** — Переименование статуса не меняет записи контрольного следа. В истории КЕ остаётся название статуса на момент события.

**Переходы**
- **F-03.BR8** — Атрибуты перехода [domain-model §3.5]:
  - из статуса, в статус;
  - название действия;
  - роли, которым переход разрешён;
  - условия (BR11);
  - «контролируемый» (BR16);
  - «требует ЭП» и значение подписи (BR15);
  - поля, которые заполняются при переходе (BR13).

  Между двумя статусами — не больше одного перехода в каждом направлении. Переход в тот же статус не задаётся. Пример: «В эксплуатации» → «На обслуживании», действие «Отправить на обслуживание».
- **F-03.BR9** — Статус КЕ меняется только переходом. Поле «Статус» в карточке напрямую не редактируется. Исключение — создание КЕ через API и импорт (BR21).
- **F-03.BR10** — Переход может выполнить пользователь с правом Update на тип КЕ (с учётом ограничения по записям, F-13), если он входит в одну из ролей перехода. Если список ролей пуст, переход доступен всем, у кого есть право Update.
- **F-03.BR11** — Виды условий перехода [P-1, P-27, OQ-4]. Выполняться должны все заданные условия перехода одновременно [ревью ВП 2026-10-14].
  1. **Заполнены указанные поля.**
  2. **Значение поля — одна из указанных записей справочника.** Пример: «Статус валидации» — «Валидирована» или «Валидирована с ограничениями».
  3. **У КЕ есть выполнение мероприятия указанного вида.** Можно ограничить давность: «не старше N дней». Пример: выполнено мероприятие вида «Квалификация OQ». В условии указывают допустимые итоги выполнения, по умолчанию «Успешно» и «С замечаниями»; аннулированные выполнения не учитываются (F-05.BR18, BR21, BR27) [B4-6a]. Пример для GxP-пакета: ввод в эксплуатацию требует «Квалификации PQ» только с итогом «Успешно».
  4. **К КЕ приложен документ указанного вида в статусе «Действующий»** (F-10). Документы, приложенные к типу КЕ, не учитываются.
- **F-03.BR12** — Пользователь видит все переходы из текущего статуса, которые доступны его ролям. Если условия перехода не выполнены, переход выполнить нельзя, и система показывает невыполненные условия. Пример для «Ввести в эксплуатацию»: «Не хватает документа вида «Отчёт о валидации». Статус валидации — «В процессе», нужно «Валидирована» или «Валидирована с ограничениями»».
- **F-03.BR13** — При переходе система спрашивает значения полей перехода. Для полей-дат по умолчанию подставляется текущая дата, и дата не может быть позже текущей. Пример: «Ввести в эксплуатацию» заполняет «Дату ввода в эксплуатацию» [S2, discovery §2.2].
- **F-03.BR14** — В регулируемой категории при переходе обязательна причина изменения [P-5, F-08]. В нерегулируемой можно оставить необязательный комментарий.
- **F-03.BR15** — Переход, требующий ЭП, выполняется только после подписи пользователя, который его выполняет. Значение подписи берётся из настройки перехода (F-12) [S1 ¶19].
- **F-03.BR16** — Контролируемый переход при включённом контроле изменений категории [P-3, F-08]:
  - не меняет статус сразу — создаётся запрос на изменение, статус меняется после согласования;
  - условия проверяются при создании запроса и ещё раз при согласовании.

  При выключенном контроле изменений признак «контролируемый» ни на что не влияет.
- **F-03.BR17** — Пока у КЕ есть активный запрос на изменение, второй запрос не создаётся [INV-12, P-4]. Поэтому:
  - контролируемые переходы КЕ недоступны;
  - если в активном запросе есть переход, недоступны и остальные переходы;
  - если в активном запросе только изменения полей, неконтролируемые переходы доступны.
- **F-03.BR18** — Каждый переход пишется в контрольный след и историю КЕ [S1 ¶20] (F-11):
  - кто и когда;
  - из какого статуса и в какой;
  - значения полей перехода;
  - причина или комментарий;
  - подпись.
- **F-03.BR19** — При переходе в конечный статус система предлагает отменить запланированные мероприятия КЕ с причиной «КЕ выведена из эксплуатации». Флажок отмены включён по умолчанию (F-05).
- **F-03.BR20** — Изменение модели — статусов, переходов, условий — действует на следующие переходы. Выполненные переходы и активные запросы на изменение не пересчитываются; исключение — повторная проверка условий при согласовании (BR16).
- **F-03.BR21** — Статус КЕ при создании и изменении через API и импорт [B2-6a]:
  - новая КЕ, созданная в интерфейсе, получает начальный статус;
  - новую КЕ, созданную через импорт (F-16) или API (F-15), можно сразу поставить в любой статус модели — это нужно для переноса существующего реестра. Условия перехода при этом не проверяются, а в контрольном следе указан способ создания;
  - статус существующей КЕ через API и импорт меняется только переходом по правилам BR10–BR17;
  - переходы, требующие ЭП, через API и импорт недоступны: ЭП ставит человек повторной аутентификацией, а клиент API — не человек. Это исключение из NFR-14; способ подписи через API, если он понадобится, решается в F-12 и F-15.

**Мягкое удаление, восстановление, очистка**
- **F-03.BR22** — Мягкое удаление предназначено для ошибочно созданных КЕ. Завершение жизни КЕ — это переход в конечный статус: в GxP удаления нет [R6a, discovery §3]. Мягкое удаление не меняет статус КЕ.
- **F-03.BR23** — Мягко удалить КЕ может пользователь с правом Delete на тип КЕ (по умолчанию — администратор системы и менеджер конфигураций). Причина обязательна [R6a]. Пример причины: «Создана дважды, дубль SRV-000045».
- **F-03.BR24** — Что происходит с мягко удалённой КЕ [глоссарий, domain-model §4.1]:
  - она не показывается в реестре, поиске, выборе КЕ для связи, анализе влияния и виджетах;
  - её мероприятия приостановлены: статус срока не считается, уведомления и задачи в таск-трекерах не создаются;
  - её связи не показываются в карточках других КЕ;
  - её код и значения уникальных полей остаются занятыми;
  - карточку можно открыть из фильтра «Мягко удалённые» реестра, если есть право Delete на тип. Карточка только для чтения, с плашкой «Мягко удалена: кто, когда, причина».
- **F-03.BR25** — КЕ нельзя мягко удалить, пока у неё есть активный запрос на изменение. Сначала по запросу должно быть принято решение, или инициатор его отзывает.
- **F-03.BR26** — Восстановить КЕ может пользователь с правом Delete на тип. КЕ возвращается в том же статусе, со всеми данными, связями и мероприятиями. Сроки мероприятий пересчитываются сразу: мероприятия, срок которых прошёл за время удаления, становятся просроченными.
- **F-03.BR27** — Очистка — окончательное удаление мягко удалённой КЕ. Условия:
  - выполняет пользователь с правом «Очистка удалённых КЕ» (по умолчанию — только администратор системы, README §5);
  - включена настройка системы «Разрешить очистку» (по умолчанию выключена) [PO 2026-10-09];
  - категория КЕ нерегулируемая [INV-18];
  - КЕ ни разу не была в регулируемой категории: если признак «Регулируемая» выключили (F-01.BR35), КЕ, созданные до выключения, очистить всё равно нельзя.

  Что удаляется: значения полей, связи, мероприятия, версии baseline, привязки документов. Документ удаляется, только если он не привязан к другим КЕ и типам КЕ. Что остаётся:
  - записи контрольного следа о КЕ [INV-16];
  - запись о самой очистке в контрольном следе.

  После очистки код КЕ снова свободен. Очистка — единственный случай удаления версий baseline. Он возможен только в нерегулируемой категории (уточнение INV-17).
- **F-03.BR28** — Очистка необратима. Перед ней система показывает, что будет удалено: число связей, мероприятий, документов. Для подтверждения нужно ввести код КЕ. Можно очистить несколько КЕ сразу — тогда для подтверждения вводят число КЕ.
- **F-03.BR29** — Мягкое удаление, восстановление и очистка пишутся в контрольный след: кто, когда, причина (F-11).

## 5. Сценарии приёмки
Пишутся при подготовке ТЗ фазы, в которую войдёт фича (допущение A-9).

## 6. Данные
Атрибуты статуса, перехода и признака мягкого удаления — в domain-model §3.5 и §4.1. Эта фича уточняет:

| Поле | Смысл | Тип (логический) | Обязательное | Правила и ограничения |
|---|---|---|---|---|
| Порядок статуса | порядок в списках и фильтрах | число | да | — |
| Условие перехода: вид | что проверяется | перечисление: поле заполнено / значение поля из списка / выполнено мероприятие вида / приложен действующий документ вида | да | BR11 |
| Условие перехода: давность мероприятия | не старше N дней | число дней | нет | пусто — давность не ограничена |
| Условие перехода: допустимые итоги | с какими итогами выполнение засчитывается | набор из «Успешно», «С замечаниями», «Неуспешно» | да, для условия «выполнено мероприятие вида» | не пустой; по умолчанию «Успешно» и «С замечаниями»; F-05.BR21 [B4-6a] |
| Поля перехода | какие поля система спрашивает при переходе | список полей | нет | BR13 |
| Способ создания КЕ | интерфейс / API / импорт | перечисление | да | пишется в контрольный след (BR21) |
| Была в регулируемой категории (КЕ) | КЕ хотя бы раз относилась к регулируемой категории | флаг | да | ставится, когда КЕ создана в регулируемой категории или признак «Регулируемая» включён у её категории; не снимается; запрещает очистку (BR27) |

## 7. Интерфейс (для дизайнера)
- **Редактор статусной модели** (в карточке категории, F-01).
  - Список статусов: цвет, признаки, порядок.
  - Переходы — таблицей «из → в» и схемой.
  - Форма перехода: роли, условия, ЭП и значение подписи, «контролируемый», поля перехода.
- **Карточка КЕ.**
  - Статус с цветом.
  - Кнопки доступных переходов. У перехода с невыполненными условиями — их список (BR12).
  - Диалог перехода: поля перехода, причина или комментарий, ЭП, предложение отменить мероприятия при переходе в конечный статус (BR19).
- **Мягкое удаление.** Тексты интерфейса — по глоссарию: «удаление» без уточнения не используется.
  - Действие «Мягко удалить» с обязательной причиной.
  - Фильтр «Мягко удалённые» в реестре.
  - Плашка «Мягко удалена» в карточке и действие «Восстановить».
- **Очистка.** Действие в фильтре «Мягко удалённые»: окно со сводкой и вводом кода КЕ или числа КЕ (BR28).

## 8. Не входит
- Запрет редактировать поля в зависимости от статуса КЕ — не в v1.
- Одна статусная модель на несколько категорий. В v1 модель копируется при создании категории (F-01.BR5).
- Отдельные модели для типов внутри категории.
- Условия «ИЛИ» и составные выражения в условиях перехода.
- Автоматические переходы по расписанию или событию.
- Переходы «из любого статуса» одной настройкой.
- Автоматическая очистка по сроку.

## 9. Допущения, решения и открытые вопросы
- **B2-6a** [ВП 2026-10-12] — при импорте и через API новую КЕ можно создать сразу в нужном статусе, без проверки условий (BR21).
- Уточнение INV-17 (BR27): очистка удаляет версии baseline вместе с КЕ. Это возможно только в нерегулируемой категории и при включённой настройке «Разрешить очистку».
