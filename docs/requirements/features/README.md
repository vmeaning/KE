## Открытые вопросы порции 2
Ответ — номер и буква, например «1a, 2b». Первым идёт рекомендованный вариант.

1. **Массовые операции в реестре** (F-02.BR16).
   - a) **(рекомендую)** Изменить неконтролируемое поле; назначить или заменить ответственного; выполнить переход без ЭП и согласования; мягко удалить; выгрузить. До 1 000 КЕ за раз, по итогам — отчёт об ошибках. Контролируемые изменения и переходы с ЭП — по одной КЕ.
   - b) То же плюс создание разового мероприятия сразу для выбранных КЕ, например «Установить обновление» на 200 серверов.
   - c) То же плюс контролируемые изменения: по каждой КЕ создаётся свой запрос на изменение.
2. **Код КЕ** (F-01.BR12, F-02.BR21).
   - a) **(рекомендую)** В типе задаётся шаблон: префикс и номер, например «SRV-000124». Код подставляется сам, пользователь может заменить его своим. Если шаблона нет, код вводят вручную.
   - b) Код всегда вводят вручную.
   - c) Код всегда присваивается автоматически, менять его нельзя.
3. **«Уникальное в типе»** (F-01.BR23, INV-9).
   - a) **(рекомендую)** Запрет: КЕ с повторяющимся значением не сохраняется — ни в интерфейсе, ни через API, ни при импорте. Предупреждение о возможном дубле остаётся только для Наименования.
   - b) Только предупреждение, как сейчас в INV-9: сохранить можно.
4. **Как КЕ связана с подразделением** (F-02.BR33). Решение R8a ввело ограничение роли «только моё подразделение», но в модели у КЕ нет подразделения.
   - a) **(рекомендую)** Новое базовое поле «Подразделение-владелец»: необязательное, по умолчанию — подразделение автора. Роль видит КЕ своего подразделения и вложенных.
   - b) Через матрицу ответственности: КЕ видна, если хотя бы один её ответственный — из моего подразделения или вложенного. Минус: КЕ без ответственных не увидит никто с таким ограничением, даже её автор.
   - c) Убрать ограничение «только моё подразделение».
5. **Смена типа КЕ** (F-02.BR31).
   - a) **(рекомендую)** Можно, но только на тип той же категории. Поля категории, статус, связи и история сохраняются, значения полей старого типа остаются в истории.
   - b) Нельзя: ошибочную КЕ мягко удаляют и создают заново. Минусы: код старой КЕ остаётся занятым, потому что очистка по умолчанию выключена; связи и история не переносятся.
6. **Статус новой КЕ при импорте и через API** (F-03.BR21).
   - a) **(рекомендую)** Новую КЕ можно сразу создать в любом статусе, без проверки условий перехода; способ создания пишется в контрольный след. Иначе перенос реестра превратится в ручное проведение тысяч КЕ по статусам.
   - b) Только в начальном статусе, дальше — переходами.
7. **Право на ведение простых справочников** (F-19.BR18, D-2a).
   - a) **(рекомендую)** Отдельное право на каждый простой справочник: кадровику можно дать «Должности», не давая «Значения подписи».
   - b) Одно право на все простые справочники.
8. **Загрузка записей справочника из Excel или CSV** (F-19.BR27).
   - a) **(рекомендую)** Да. Колонки: «Код», «Название», «Код родителя», «Порядок», «Действует». Местоположений и должностей бывают сотни.
   - b) Нет: записи вводят вручную или переносят пакетами конфигурации (F-17).
9. **Конструктор карточек: что ещё в v1** (F-01.BR13, BR18, BR33). В [S1 ¶7] ВП просил предложений.
   - a) **(рекомендую)** Ширина поля (вся строка или половина), предпросмотр карточки, копирование типа, готовые форматы строк: IPv4, IPv6, MAC-адрес, имя хоста.
   - b) Всё из a плюс условная видимость полей: поле показывается, только когда другое поле имеет нужное значение.
   - c) Ничего сверх доменной модели.
10. **Связи и контроль изменений** (F-04.BR17). Решение OQ-2 убрало связи из baseline, а про контроль изменений решения нет. Для GxP это важно (Annex 11 §10).
    - a) **(рекомендую)** В v1 связи не контролируются: создаются и удаляются сразу. В регулируемой категории нужна причина изменения, а всё видно в истории обеих КЕ. Значимые изменения инфраструктуры и так проходят через контролируемые поля и переходы.
    - b) У типа связи — флажок «Контролируемый»: в категории с включённым контролем изменений создание и удаление связи такого типа идёт через запрос на изменение.

## Как читать файл фичи
- `F-NN.USm` — user story, `F-NN.BRk` — бизнес-правило. Ссылка на правило другой фичи — полным ID, например `F-01.BR23`.
- В квадратных скобках — источник правила: `[S1 ¶N]`, решение ВП, `INV-n`, раздел доменной модели.
- `[PROPOSAL]` — предложение Аналитика без источника: ВП утверждает его вместе с порцией.
- `[вопрос N]` — правило записано по рекомендованному варианту открытого вопроса к ВП. Если ВП выберет другой вариант, правило меняется.
