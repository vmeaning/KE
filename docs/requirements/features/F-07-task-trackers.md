# F-07. Таск-трекеры

> Статус: draft · Приоритет: Must
> Источник: S1 ¶3, ¶11–12, R11a, R13a, B4-6a (6.2a), B4-11c, B4-12a, B4-13a [ВП 2026-10-17]; ревью ВП 2026-10-10 (исполнитель — пользователь трекера); A-2, A-6; INV-21; domain-model §3.7, §5.3, §7.4
> Зависит от: F-05 · Связано: F-06, F-13 (замещение), F-15 (API), F-17 (пакеты) · Экраны: появятся у дизайнера

## 1. Цель
Работы по мероприятиям исполняются там, где IT-служба уже работает, — в таск-трекере, а KE хранит план, факт и подтверждение (A-2). Фича решает задачу, если:
- к сроку мероприятия в трекере появляется задача на нужного человека со ссылкой на КЕ;
- в карточке КЕ виден ключ и статус задачи;
- после выполнения или отмены мероприятия в трекере не остаётся висящих задач.

## 2. Роли и права
| Действие | Право | Роли по умолчанию |
|---|---|---|
| Подключать трекеры | «Интеграции, каналы уведомлений, клиенты API» | администратор системы |
| Задавать правила задач в мероприятии | «Создание и настройка мероприятий КЕ» | администратор системы, менеджер конфигураций, инженер |
| Задавать правила задач в шаблоне | «Настройка категорий, типов, …, шаблонов мероприятий» | администратор системы, администратор конфигурации |
| Видеть связанные задачи | доступ к мероприятию (F-05) | — |

## 3. User stories
- **F-07.US1** — Как пользователь с правом «Интеграции, каналы уведомлений, клиенты API», я хочу подключить Яндекс Трекер или Jira и проверить подключение, чтобы KE ставил задачи в нашу очередь [S1 ¶3] [B4-11c].
- **F-07.US2** — Как пользователь с правом «Интеграции, каналы уведомлений, клиенты API», я хочу подключить другой трекер через универсальный коннектор, чтобы не ждать доработки продукта [B4-11c].
- **F-07.US3** — Как пользователь с правом «Создание и настройка мероприятий КЕ», я хочу задать в мероприятии правила задач — трекер, очередь, за сколько дней, исполнителя, текст со ссылкой на КЕ, — чтобы работа пришла исполнителю вовремя [S1 ¶11] [B4-12a].
- **F-07.US4** — Как пользователь, ответственный за мероприятие, я хочу видеть в мероприятии ключ, ссылку и статус задачи, чтобы не переключаться между системами [R11a].
- **F-07.US5** — Как пользователь трекера, исполнитель задачи, я хочу, чтобы после выполнения или отмены мероприятия в KE задача закрылась с комментарием, а при переносе срока — сменила срок, чтобы в трекере не копились неактуальные задачи [B4-13a].

## 4. Бизнес-правила

**Подключения** [domain-model §7.4]
- **F-07.BR1** — Виды подключения — перечисление продукта [B4-11c]:
  - Яндекс Трекер;
  - Jira Cloud;
  - Jira Server / Data Center;
  - универсальный коннектор (BR3).

  Подключений может быть несколько, в том числе одного вида. Встроенные коннекторы Redmine и YouTrack — roadmap; до тех пор их подключают через универсальный коннектор.
- **F-07.BR2** — Атрибуты подключения: название, вид, адрес, учётные данные, очередь или проект по умолчанию, тип задачи по умолчанию, статус закрытия (BR9), «Искать пользователей по e-mail» (BR5), «действует». Учётные данные хранятся зашифрованными и не попадают в пакеты конфигурации, выгрузки и логи (INV-21). Кнопка «Проверить подключение» показывает, удалось ли войти и видна ли очередь. Яндекс Трекер и Jira Cloud — облачные сервисы: KE достучится до них, только если из контура заказчика есть выход в интернет (A-6). В закрытом контуре — Jira Server / Data Center или универсальный коннектор.
- **F-07.BR3** — Универсальный коннектор [B4-11c]:
  - KE отправляет POST-запрос с JSON на адрес подключения: создать задачу, изменить срок или исполнителя, добавить комментарий, закрыть;
  - в JSON — то же, что во встроенных коннекторах: очередь, заголовок, текст, срок, исполнитель (идентификаторы, как в F-06.BR3), наблюдатели, ссылка на КЕ и мероприятие;
  - внешняя система возвращает ключ и ссылку задачи в ответе, а статус задачи потом сообщает через API KE (F-15);
  - формат описан в документации администратора и имеет номер версии.

**Правило задачи** [S1 ¶11, domain-model §3.7]
- **F-07.BR4** — Правило задачи в мероприятии и шаблоне:
  - подключение и очередь или проект — по умолчанию из подключения;
  - когда — «за N дней» до плановой даты; 0 — в день плановой даты;
  - исполнитель (BR5);
  - заголовок и текст — шаблон с подстановками: код, наименование и ссылка на карточку КЕ, название и вид мероприятия, плановая дата, ответственный [S1 ¶11].

  Правил в мероприятии может быть несколько, например задача инженеру за 7 дней и задача подрядчику за 3 дня. Правила копируются из шаблона и редактируются в мероприятии (F-05).
- **F-07.BR5** — Исполнитель задачи [B4-12a]:
  - **конкретный пользователь трекера** — выбирается из списка пользователей трекера через подключение [ревью ВП 2026-10-10];
  - **«ответственный мероприятия»** — система находит пользователя трекера по логину, а если не нашла — по e-mail сотрудника. `[PROPOSAL]` Поиск по e-mail передаёт персональные данные во внешнюю систему, поэтому работает, только если в подключении включено «Искать пользователей по e-mail»; по умолчанию выключено, как передача e-mail в вебхуке (F-06.BR3). Если сопоставить не удалось, задача ставится без исполнителя, в тексте указан ответственный, а пользователи с правом «Интеграции, каналы уведомлений, клиенты API» получают уведомление (F-06). E-mail при этом не показывается (INV-28);
  - **без исполнителя** — задача попадает в очередь.

  `[PROPOSAL]` Если у ответственного на момент создания задачи действует замещение (F-13.BR47), исполнитель — заместитель, а ответственный — наблюдатель. Позже начавшееся или закончившееся замещение исполнителя не меняет.
- **F-07.BR6** — Одна работа — одна задача [B4-6a, 6.2a]. Если о задаче должны знать двое — ответственный и его заместитель, исполнитель и подтверждающий, — система ставит одну задачу: исполнитель — один, остальные — наблюдатели. Если наблюдателя не удалось найти в трекере, его ФИО указывается в тексте задачи. Так создаётся и задача разбора неуспешного итога (F-05.BR20).
- **F-07.BR7** — Задача создаётся один раз на каждое правило и каждую плановую дату. У регулярного мероприятия на каждую плановую дату — своя задача. Если плановую дату перенесли до момента создания задачи, задача создаётся по новой дате. Исключение — аннулирование выполнения (BR9). Задачи не создаются, пока мероприятие приостановлено или КЕ не в эксплуатационном статусе (F-05.BR31). Массовое создание мероприятий (F-02.BR16) создаёт задачи по каждой КЕ отдельно.

**Жизнь задачи** [R11a, B4-13a]
- **F-07.BR8** — Связанная задача (domain-model §5.3) хранит ключ, ссылку, последний известный статус и время его получения. Ключ, ссылка и статус видны в строке мероприятия. `[PROPOSAL]` Статус обновляется не реже раза в 15 мин; как именно — опросом или по событиям трекера — решает Архитектор.
- **F-07.BR9** — KE поддерживает задачу в актуальном состоянии [B4-13a]:
  - **мероприятие выполнено или отменено** — KE пишет в задачу комментарий (итог или причина отмены, кто, когда, ссылка) и переводит её в статус закрытия из подключения. Если статус закрытия не задан или перевод невозможен в схеме задачи, KE только пишет комментарий;
  - **перенесена плановая дата** — KE меняет срок задачи;
  - **сменился ответственный** — KE меняет исполнителя, если в правиле исполнитель — «ответственный мероприятия»;
  - **выполнение аннулировано** (F-05.BR27) — KE пишет комментарий в закрытую задачу. Задачи, созданные для следующей плановой даты, KE закрывает с комментарием. Закрытые задачи KE заново не открывает. `[PROPOSAL]` Если момент «за N дней» для восстановленной плановой даты уже наступил, KE создаёт новую задачу со ссылкой на прежнюю в тексте.
- **F-07.BR10** — Закрытие задачи в трекере мероприятие не выполняет [R11a]. `[PROPOSAL]` Если задача закрыта, а выполнение в KE не подтверждено, в строке мероприятия и в «Моих делах» ответственного видна пометка «Задача закрыта, выполнение не подтверждено».
- **F-07.BR11** — `[PROPOSAL]` Ошибки. Создание и обновление задачи повторяются, как отправка уведомлений (F-06.BR5): по умолчанию 3 попытки через 5 мин. Если все попытки не удались:
  - задача получает пометку «Ошибка» с текстом ошибки трекера;
  - в мероприятии есть кнопка «Повторить»;
  - ответственный и пользователи с правом «Интеграции, каналы уведомлений, клиенты API» получают уведомление (F-06).
- **F-07.BR12** — Если подключение сделали недействующим, новые задачи по нему не создаются, а в правилах мероприятий подключение помечено. Существующие связанные задачи остаются в мероприятиях со ссылками.
- **F-07.BR13** — В текст задачи попадают только поля из подстановок BR4. Контактные данные в задачу не попадают (INV-28).
- **F-07.BR14** — В контрольный след пишутся создание, изменение и отключение подключений (F-11). `[PROPOSAL]` Создание задачи и её закрытие из KE пишутся в историю КЕ с ключом задачи.

## 5. Сценарии приёмки
Пишутся при подготовке ТЗ фазы, в которую войдёт фича (допущение A-9).

## 6. Данные
Подключение и связанная задача — domain-model §7.4, §5.3; правило задачи — §3.7. Фича добавляет:

| Поле | Смысл | Тип (логический) | Обязательное | Правила и ограничения |
|---|---|---|---|---|
| Вид подключения | + «Универсальный коннектор» | перечисление | да | BR1, BR3 |
| Статус закрытия (подключение) | в какой статус переводить задачу | строка (статус трекера) | нет | BR9 |
| «Искать пользователей по e-mail» (подключение) | можно ли искать исполнителя по e-mail сотрудника | флаг | да | по умолчанию выключено; BR5 |
| Режим исполнителя (правило) | пользователь трекера / ответственный мероприятия / без исполнителя | перечисление + пользователь трекера | да | BR5 [B4-12a] |
| Наблюдатели (связанная задача) | кто ещё следит за задачей | список | нет | BR6 |
| Состояние создания (связанная задача) | создана / ошибка с текстом | перечисление + текст | да | BR11 |

## 7. Интерфейс (для дизайнера)
- **Администрирование → Таск-трекеры:** список подключений, форма с выбором вида, «Проверить подключение», статус закрытия, «Сделать недействующим».
- **Настройки мероприятия и шаблона:** правила задач — подключение, очередь, «за N дней», исполнитель (три режима; поиск пользователя трекера), заголовок и текст с подстановками и предпросмотром.
- **Строка мероприятия:** ключ задачи — ссылка в трекер, статус, время обновления, пометки «Ошибка» с кнопкой «Повторить» и «Задача закрыта, выполнение не подтверждено».

## 8. Не входит
- Встроенные коннекторы Redmine и YouTrack — roadmap [B4-11c].
- Подтверждение выполнения мероприятия по закрытию задачи (R11a).
- Перенос комментариев и вложений из трекера в KE.
- Создание мероприятий из задач трекера.
- Задачи по другим событиям — согласованиям, качеству данных — и учёт трудозатрат.
