## 1. Справочники и перечисления

По решению ВП (комментарий к §5.5 discovery) **любой выбираемый из списка параметр — справочник**. Исключения — перечисления продукта.

**Справочник** — общее понятие, как в 1С [PO 2026-10-10, D-1a]. Все справочники находятся в разделе интерфейса «Справочники». Они бывают двух видов:
- **простые** — список значений с одинаковым набором реквизитов. Заказчик может создавать свои без программиста;
- **встроенные** — со своими реквизитами и логикой продукта: Организации, Подразделения, Сотрудники, Контрагенты, Контактные лица, Типы связей. Их структуру задаёт продукт, наполнение — заказчик.

Право на ведение каждого встроенного справочника и простых справочников — отдельное. Его можно назначить любой роли (D-2a, README §5).

**Простой справочник** (`SimpleDirectory`):

| Атрибут | Тип | Обяз. | Правила |
|---|---|---|---|
| Код | строка | да | латиница, уникален в установке, после создания не меняется |
| Название | строка | да | — |
| Описание | текст | нет | — |
| Иерархический | флаг | да | записи образуют дерево (например, Местоположения) |
| Системный | флаг | да | справочник поставлен продуктом или пакетом. Удалить нельзя, состав записей менять можно |

**Запись справочника** (`DirectoryEntry`):

| Атрибут | Тип | Обяз. | Правила |
|---|---|---|---|
| Справочник | ссылка | да | — |
| Код | строка | да | уникален в справочнике, после создания не меняется |
| Название | строка | да | — |
| Родитель | ссылка на запись | нет | только для иерархических справочников |
| Порядок | число | да | порядок в списках выбора |
| Цвет | цвет | нет | для статусов, критичности и т.п. |
| Действует | флаг | да | недействующую запись нельзя выбрать в новых данных; уже сохранённые значения остаются |
| Системная запись | флаг | да | от записи зависит логика продукта или пакета: переименовать можно, удалить или деактивировать нельзя |

**Простые справочники, которые поставляются с продуктом.** Значения — примеры: заказчик меняет их под себя, кроме системных записей.

| Справочник | Назначение | Как используется | Примеры значений |
|---|---|---|---|
| **Критичность** | Насколько КЕ важна для бизнеса и IT | <ul><li>базовое поле каждой КЕ</li><li>фильтр и сортировка реестра</li><li>колонка в анализе влияния и в блоке «Связанные КЕ» — сразу видно, задето ли критичное</li><li>в roadmap — фильтр рассылки о плановых работах (F-30): «предупреждать только по критичным зависимым КЕ»</li></ul> | Высокая, Средняя, Низкая |
| **Роли ответственности** | Какую ответственность сотрудник несёт за КЕ | <ul><li>матрица ответственности в карточке: роль + сотрудник + основной / замещающий [S2]</li><li>в шаблоне мероприятия: «ответственный по умолчанию — тот, кто в роли X», например периодический пересмотр назначается владельцу системы</li><li>кому слать уведомления о КЕ</li><li>ограничение доступа «только КЕ, где я ответственный» (R8a)</li></ul> | Владелец системы, Владелец процесса, ИТ-сопровождение, Бизнес-владелец |
| **Виды документов** | Что за документ привязан к КЕ | <ul><li>выбирается при прикреплении документа</li><li>фильтр и группировка документов в карточке</li><li>**условия переходов статуса**: «приложен действующий документ вида X» — в GxP-пакете ввод в эксплуатацию требует URS, оценки рисков, протоколов IQ/OQ/PQ и отчёта о валидации (P-27)</li><li>требование вложения нужного вида при выполнении мероприятия</li></ul> | Инструкция пользователя, Матрица прав доступа, URS, Оценка рисков, Протокол IQ / OQ / PQ, Отчёт о валидации, Отчёт об аудите поставщика |
| **Статусы документов** | Действует ли документ | <ul><li>выбирается у документа</li><li>условия переходов статуса учитывают только документы в статусе «Действующий» — отменённый протокол не откроет ввод в эксплуатацию</li><li>фильтр документов</li></ul> | Черновик, **Действующий** (системная запись), Устаревший (заменён новой версией), Отменён (отозван без замены) |
| **Виды мероприятий** | Что за работа планируется по КЕ | <ul><li>выбирается в шаблоне и в мероприятии</li><li>фильтры сквозного реестра и календаря мероприятий: «все поверки в ноябре»</li><li>**условия переходов статуса**: «выполнено мероприятие вида X»</li><li>виджеты и выгрузки для инспекции: «история периодических пересмотров»</li></ul> | Техническое обслуживание, Поверка, Резервное копирование, Периодический пересмотр, Квалификация IQ / OQ / PQ, **Аттестация данных** (системная: её выполнение обновляет дату последнего подтверждения актуальности КЕ, P-24) |
| **Значения подписи** | Что юридически означает электронная подпись (21 CFR Part 11 §11.50 требует указывать смысл подписи) | <ul><li>в настройках ЭП на действии (переход, выполнение мероприятия, согласование, baseline) выбирается значение</li><li>подписант видит его в окне подписи</li><li>значение сохраняется в подписи и показывается в истории и выгрузках: «Иванов И.И., 10.10.2026 14:05, Утверждаю»</li></ul> | Утверждаю, Согласовано, Выполнено, Проверено, Ознакомлен |
| **Причины отмены мероприятия** | Почему запланированное мероприятие не будет выполнено | <ul><li>обязательна при отмене мероприятия, вместе с комментарием</li><li>пишется в историю КЕ</li><li>отчёты: «какие периодические пересмотры отменены и почему» — на инспекции отмена должна быть обоснована</li></ul> | КЕ выведена из эксплуатации, Заменено другим мероприятием, Создано ошибочно, Прочее |
| **Местоположения** (иерархический) | Где физически находится КЕ | <ul><li>базовое поле КЕ</li><li>фильтр реестра с вложенными уровнями: «всё в корпусе 2»</li><li>из местоположения — переход к списку КЕ в нём [S2]</li><li>в roadmap — основа QR-инвентаризации (F-24)</li></ul> | Площадка «Москва» → Корпус 2 → Этаж 3 → Помещение 214 → Рабочее место 5 |
| **Роли контрагента** | Кем внешняя организация приходится КЕ | <ul><li>в таблице «Внешние контакты» карточки КЕ (§4.6)</li><li>фильтр «все КЕ поставщика X»</li></ul> | Поставщик, Производитель, Подрядчик |
| **Должности** | Единый список должностей сотрудников | <ul><li>реквизит сотрудника</li><li>пополняется при синхронизации с AD и 1С:ЗУП</li><li>фильтр сотрудников</li></ul> | Руководитель службы ИТ, Системный администратор, Инженер по валидации |

**Справочники GxP-пакета** (discovery §5.5) — поля карточки компьютеризированной системы:

| Справочник | Назначение | Как используется | Значения |
|---|---|---|---|
| **GxP-значимость** | К какой области регулирования относится система | <ul><li>поле карточки</li><li>фильтр реестра: «все GMP-системы» — первое, что просит инспектор (Annex 11 §4.3)</li></ul> | GMP, GDP, GLP, GCP, GVP, Не применимо |
| **Категория GAMP 5** | Тип ПО по GAMP 5; от него зависит объём валидации: для категории 5 (заказное ПО) — полный цикл, для 1 (инфраструктура) — минимум | <ul><li>поле карточки</li><li>фильтр и отчёт</li><li>администратор учитывает её, когда решает, какие мероприятия и документы обязательны для типа</li></ul> | 1, 3, 4, 5 |
| **Влияние** | Оценка влияния системы на безопасность пациента, качество продукта и целостность данных — три поля с этим справочником | <ul><li>поля карточки</li><li>основа для оценки риска</li><li>фильтр</li></ul> | Прямое, Косвенное, Нет |
| **Риск** | Итог регуляторной оценки риска системы. **Не путать с критичностью**: критичность — важность для бизнеса и IT, риск — последствия для пациента, качества и данных. У системы бухгалтерии может быть высокая критичность и низкий GxP-риск | <ul><li>поле карточки</li><li>фильтр и виджеты</li><li>по нему администратор выбирает интервал периодического пересмотра (обычно 12–36 месяцев); автоматического выбора в v1 нет</li></ul> | Высокий, Средний, Низкий |
| **Статус валидации** | Где система находится в цикле валидации (OQ-4: отдельное поле, изменение — контролируемое, с ЭП) | <ul><li>поле карточки</li><li>виджет «распределение по статусам валидации»</li><li>фильтр</li><li>условие перехода «Ввести в эксплуатацию» в GxP-пакете</li></ul> | Не оценивалась, Не требуется, Запланирована, В процессе, **Валидирована**, **Валидирована с ограничениями** (системные записи пакета: на них опирается условие перехода), Требуется ревалидация, Выведена |

**Удаление записей.** Запись справочника, которая где-то используется (в КЕ, документе, шаблоне, настройке или условии перехода), удалить нельзя — только сделать недействующей (INV-23).

Администратор создаёт свои **простые справочники** для настраиваемых полей (P-14).

**Перечисления продукта** — фиксированные списки, новое значение в которых требует кода:
- типы данных полей;
- виды каналов уведомлений;
- виды таск-трекеров;
- статусы мероприятия, запроса на изменение и задания на согласование;
- действия контрольного следа;
- единицы интервала (день, неделя, месяц, год).

Названия значений перечислений переводятся механизмом локализации.

**Встроенные справочники** описаны в своих разделах: Организации (§2.1), Подразделения (§2.2), Сотрудники (§2.3), Контрагенты и Контактные лица (§2.8), Типы связей (§3.6). Настраиваемые поля у встроенных справочников — позже (OQ-1).

## 2. Организации и люди

### 2.1 Организация `Organization` [R2-2a]
Код (уникальный, неизменяемый), наименование, ИНН (нет), действует (да).
- Измерение данных: у каждой КЕ есть организация-владелец.
- Конфигурация (категории, типы, справочники, роли) — общая на всю установку.

### 2.2 Подразделение `Department`
Организация (да), родитель (нет — дерево), код, наименование, руководитель (сотрудник, нет), действует.

### 2.3 Сотрудник `Employee` [R7a]

### 2.5 Клиент API `ApiClient` [S1 ¶24]
Название, токены (хранятся только хэши; у токена может быть срок действия или, по явному выбору администратора, бессрочный токен), роль, флаг «изменения по API принимаются без согласования» [S1 ¶22] (в регулируемой категории — см. OQ-5), ответственный сотрудник, состояние.

### 2.6 Роль `Role` [S1 ¶5–6, R8a, P-21]
| Атрибут | Правила |
|---|---|
| Код, название | код неизменяем |
| Доступные разделы | разделы интерфейса: реестр, мероприятия, мои дела, отчёты, администрирование и т.д. |
| Права на действия | перечисление действий из матрицы прав README §5 |
| Права по категориям и типам КЕ | для каждого типа: Create / Read / Update / Delete. **Новый тип — права пустые у всех ролей, кроме администратора** [S1 ¶6] |
| Ограничение по записям | организации (список или «все»); «только моё подразделение»; «только где я ответственный» |
| Видит историю КЕ | отдельное право [S1 ¶5] |
| Системная | роль «Администратор системы» нельзя удалить и лишить прав |

**Сложение ролей**: у пользователя действует объединение прав всех его ролей, «разрешение побеждает запрет» [S1 ¶5]. Ограничения по записям тоже объединяются: КЕ видна, если её разрешает хотя бы одна роль.

### 2.7 Замещение `Substitution` [P-2]
Кого замещают, кто замещает, период (с, по), область (согласование изменений; в будущем другие полномочия). Действия заместителя пишутся в контрольный след «от имени».

### 2.8 Контрагент `Counterparty` и Контактное лицо `Contact` [S2, R13a]
- **Контрагент** — встроенный справочник. Атрибуты: код (неизменяемый), наименование, ИНН (нет), действует.
- **Контактное лицо** — встроенный справочник. Атрибуты: контрагент (обязательно), ФИО, должность (строка), телефон (тип «телефон»), e-mail, действует.
- **Внешние контакты КЕ** (§4.6) ссылаются на контрагентов и их контактных лиц.

| Описание | необязательно; для чего тип |
| Иконка | необязательна; если не задана — иконка категории |
| Настраиваемые поля типа | добавляются к полям категории |
| Шаблон карточки | порядок и группировка полей категории и типа, элементы оформления |
| Ответственные типа | список сотрудников-подсказок при выборе ответственных; флаг «только указанные ответственные» [S1 ¶10] |
| Шаблоны мероприятий типа | добавляются к шаблонам категории [S1 ¶13] |
| Ссылки и документы | P-11 |
| Действует | недействующий тип нельзя выбрать для новых КЕ. Деактивация запрещена, пока есть КЕ этого типа в статусах, кроме конечных [S2] |

### 3.3 Определение поля `FieldDefinition` [S1 ¶7–9, P-6, P-8, P-12]
| Атрибут | Правила |
|---|---|
| Владелец | категория или тип |
| Код | латиница; задаётся при создании (предлагается из названия); после сохранения **не меняется**. Уникален в пределах категории вместе со всеми её типами |
| Название, подсказка | меняются свободно |
| Тип данных | перечисление: строка, текст, число (целое или дробное; единица, мин., макс., точность), дата, дата-время, флаг, значение справочника (одно или несколько), сотрудник, контрагент, местоположение, URL, e-mail, **телефон**. **После появления данных не меняется** |
| Обязательное | можно включить в любой момент, см. INV-6 |
| Значение по умолчанию | — |
| Проверка | маска (регулярное выражение) для строк; диапазон для чисел и дат |
| Тип «телефон» | номер проверяется при вводе и хранится в международном формате. Российские номера, введённые с «8» или «+7», приводятся к «+7». При вводе цифры группируются: «+7 (912) 333-22-22». Номера других стран вводятся с кодом страны [ревью ВП 2026-10-10] |
| Уникальное в типе | например, серийный номер |
| Контролируемое | изменение требует согласования при включённом контроле изменений категории (P-3) |
| Контролируемая дата | только для дат: уведомления за N дней (до трёх сроков) и подсветка (P-8) |
| Только для чтения в интерфейсе | заполняется через API или импорт |
| Архивировано | P-6 |

**Базовые поля** (P-13) есть у каждой КЕ, удалить их нельзя:
- Код, Наименование, Тип, Статус, Критичность;
- Организация-владелец и «Общая для организаций»;
- Местоположение, Описание;
- Ответственные (матрица);
- Дата ввода в эксплуатацию, Дата вывода из эксплуатации;
- служебные: создана (кем, когда), изменена (кем, когда), дата последнего подтверждения актуальности (P-24).

### 3.4 Элемент оформления `LayoutElement` [S1 ¶7]
Группа полей (заголовок, сворачиваемая), разделитель, текстовый блок (подсказка). Удаляется в любой момент [S1 ¶9].

### 3.5 Статусная модель `LifecycleModel` [R2a, P-1]
- **Статус**: код (неизменяемый), название, цвет, признаки:
  - начальный — ровно один на модель;
  - эксплуатационный — по таким КЕ считаются мероприятия и уведомления;
  - конечный — например, «Выведена из эксплуатации», «Списана».
- **Переход** (`Transition`):
  - из статуса, в статус, название действия;
  - роли, которым разрешён;
  - **условия**: заполнены указанные поля; выполнены мероприятия указанных видов; приложены документы указанных видов (P-27);
  - контролируемый — требует согласования (P-3);
  - требует ЭП со значением подписи;
  - что заполняется при переходе: например, дата ввода в эксплуатацию.

Пример модели «Базового ИТ-пакета» (настраивается): Планируется → Внедрение → В эксплуатации ⇄ На обслуживании → Выведена из эксплуатации → Списана.

Мягкое удаление — не статус, а отдельный признак КЕ (§4.1).

### 3.6 Тип связи `RelationshipType` [S1 ¶16, P-7, W-3c]
| Атрибут | Правила |
|---|---|
| Код | неизменяем |
| Прямое название, обратное название | «Входит в» / «Включает в себя». Для симметричного типа названия совпадают («Взаимодействует с») |
| Направление влияния | от цели к источнику / от источника к цели / в обе стороны / нет влияния |
| Допустимые пары | список (категория или тип источника, категория или тип цели). Пустой список — любые пары |
| Иерархический | для таких типов запрещены циклы |

### 3.7 Шаблон мероприятия `ActivityTemplate` [S1 ¶11–13, R9a, P-9, P-29]
| Атрибут | Правила |
|---|---|
| Владелец | категория или тип |
| Название, вид мероприятия | вид — запись справочника |
| Регулярное / разовое | — |
| Интервал | число и единица (день, неделя, месяц, год); отсчёт — от фактической или от плановой даты (R9a) |
| Обязательное | у каждой КЕ этого типа обязательно должно быть такое мероприятие [S1 ¶13] |
| Ответственный по умолчанию | роль ответственности из матрицы КЕ (например, «Владелец системы») |
| Результат обязателен | [S1 ¶11] |
| Требуется ЭП | со значением подписи [S1 ¶11] |
| Требуется вложение | — |
| Уведомления | список правил: каналы, за сколько дней (до трёх сроков) [S1 ¶11] |
| Задачи в трекере | список правил: подключение, **исполнитель — пользователь таск-трекера** (выбирается из списка пользователей трекера через подключение, потому что пользователи KE и трекера не совпадают один к одному), за сколько дней, шаблон текста со ссылкой на КЕ [S1 ¶11, ревью ВП 2026-10-10] |
| Чек-лист | пункты: текст, обязательный, тип ответа — отметка / значение (единица, допуск) / файл |

Изменение шаблона не меняет мероприятия, уже созданные у КЕ. Администратор может применить изменение к существующим мероприятиям массово (P-9).

### 4.2 Ответственность `Responsibility` [P-10, S2]
КЕ, роль ответственности, сотрудник, основной / замещающий. На одну роль ответственности — не больше одного основного.

### 4.3 Связь `Relationship` [S1 ¶16, P-7, W-3c]
Источник, цель, тип связи, комментарий, кто и когда создал. **Весов у связей нет** (решение ВП W-3c).
- Хранится **одна** запись.
- В карточке источника она показывается под прямым названием типа, в карточке цели — под обратным.

### 4.4 Документ `Document` [S1 ¶18, P-11]
Вид документа, название, файл **или** ссылка (ровно одно из двух), версия, дата, статус документа (справочник «Статусы документов»), связи с КЕ и типами КЕ (многие ко многим), кто загрузил, контрольная сумма файла.

### 4.5 Baseline `Baseline` [S1 ¶17, R10a, P-15]
КЕ, номер версии (1, 2, …), снимок значений всех полей и статуса КЕ на момент создания (связи — в следующей версии, OQ-2), причина, кто и когда создал, ЭП (если требуется), признак «текущий». Версии не изменяются и не удаляются.

### 4.6 Внешний контакт КЕ `ExternalContact` [S2, R13a]
Таблица в карточке КЕ:
- роль контрагента — простой справочник «Роли контрагента»: Поставщик, Производитель, Подрядчик;
- контрагент;
- контактное лицо — выбирается только из контактов этого контрагента;
- примечание.

## 8. Конфигурация продукта и настройки

- **Пакет конфигурации** `ConfigPackage` [S1 ¶4, P-19]: версия формата, версия продукта, манифест (что включено), содержимое, контрольная сумма, кто и когда выгрузил. **Журнал импорта**: режим (в чистую систему / слияние), результат предварительного просмотра, применённые изменения.
- **Настройки системы**:
  - порог «близкий срок» в днях [S1 ¶15];
  - через сколько дней скрывать выполненные разовые мероприятия [S1 ¶14];
  - порог «устаревшая КЕ» (P-28);
  - анализ влияния: глубина по умолчанию 3, максимум 5 (W-4a);
  - блок «Связанные КЕ»: глубина по умолчанию 1; окно недавних изменений и окно плановых работ — по умолчанию 14 дней (W-2a, W-5a);
  - «Разрешить очистку» — по умолчанию выключено [PO 2026-10-09];
  - политика паролей, тайм-аут сессии, число неудачных входов до блокировки;
  - оформление: логотип, основные цвета [S1 ¶26].
- **Сохранённое представление** `SavedView` [S1 ¶25]: владелец, личное или общее, фильтры, колонки, сортировка. Последние фильтры пользователя запоминаются автоматически.

## 9. Жизненные циклы

### 9.1 КЕ: мягкое удаление (независимо от статуса)
```mermaid
stateDiagram-v2
    [*] --> Активна
    Активна --> Удалена: удалить (право Delete, причина)
    Удалена --> Активна: восстановить
    Удалена --> [*]: очистка (администратор - настройка «Разрешить очистку» включена - категория нерегулируемая)
```

### 9.2 Мероприятие
```mermaid
stateDiagram-v2
    [*] --> Запланировано
    Запланировано --> Запланировано: выполнено (регулярное) / новая плановая дата
    Запланировано --> Выполнено: выполнено (разовое)
    Запланировано --> Отменено: отменить (причина)
    Выполнено --> [*]
    Отменено --> [*]
```
Статус срока («просрочено», «близкий срок») вычисляется у мероприятий в состоянии «Запланировано» и только для КЕ в эксплуатационных статусах, не удалённых.

### 9.3 Запрос на изменение и задания
```mermaid
stateDiagram-v2
    [*] --> НаСогласовании
    НаСогласовании --> Согласован: первый согласующий согласовал → изменения применены
    НаСогласовании --> Отклонён: первый согласующий отказал (комментарий)
    НаСогласовании --> Отозван: инициатор отозвал
    Согласован --> [*]
    Отклонён --> [*]
    Отозван --> [*]
```
Когда запрос выходит из состояния «На согласовании», все его активные задания становятся «Неактуально». Их владельцы получают уведомление о результате, а действия «Согласовать» и «Отказать» им недоступны (P-2, R2-1a).

### 9.4 Пользователь
Активен ⇄ Заблокирован (N неудачных входов или вручную) → Отключён (сотрудник уволен или учётная запись отключена вручную).

### 9.5 Доставка уведомления
В очереди → Отправлено | Ошибка (после N попыток с паузой) | Нет адреса получателя.

## 11. Открытые вопросы к модели

- **OQ-1.** ~~Нужны ли настраиваемые поля у Сотрудников, Контрагентов и Местоположений?~~ **Решено [PO 2026-10-09]:** не в v1, позже.
- **OQ-2.** ~~Входят ли связи и мероприятия в снимок baseline?~~ **Решено [PO 2026-10-09]:** в v1 baseline — значения полей и статус. Связи — в следующей версии.
- **OQ-3** (Архитектору). Как подписывают пользователи SSO, у которых нет пароля в KE? Варианты: повторный вход через SSO, отдельный PIN подписи, пароль LDAP.
- **OQ-5** (к фичам F-08 и F-15). Действует ли флаг клиента API «изменения принимаются без согласования» в регулируемой категории? Варианты: (a) не действует — в регулируемой категории изменения по API тоже идут через согласование (рекомендация: иначе интеграция обходит контроль изменений); (b) действует, каждое такое изменение помечается в контрольном следе; (c) решает администратор отдельной настройкой категории.
