## 1. Справочники и перечисления

По решению ВП (комментарий к §5.5 discovery) **любой выбираемый из списка параметр — справочник**. Исключения — перечисления продукта.

**Справочник** — общее понятие, как в 1С [PO 2026-10-10, D-1a]. Все справочники находятся в разделе интерфейса «Справочники». Они бывают двух видов:
- **простые** — список значений с одинаковым набором реквизитов. Заказчик может создавать свои без программиста;
- **встроенные** — со своими реквизитами и логикой продукта: Организации, Подразделения, Сотрудники, Контрагенты, Контактные лица, Типы связей. Их структуру задаёт продукт, наполнение — заказчик.

Право на ведение каждого встроенного справочника и простых справочников — отдельное. Его можно назначить любой роли (D-2a, README §5).

**Простой справочник** (`SimpleDirectory`):

| Атрибут | Тип | Обяз. | Правила |
|---|---|---|---|
| Код | строка | да | латиница, уникален в установке, после создания не меняется |
| Название | строка | да | — |
| Описание | текст | нет | — |
| Иерархический | флаг | да | записи образуют дерево (например, Местоположения) |
| Системный | флаг | да | справочник поставлен продуктом или пакетом. Удалить нельзя, состав записей менять можно |

**Запись справочника** (`DirectoryEntry`):

| Атрибут | Тип | Обяз. | Правила |
|---|---|---|---|
| Справочник | ссылка | да | — |
| Код | строка | да | уникален в справочнике, после создания не меняется |
| Название | строка | да | — |
| Родитель | ссылка на запись | нет | только для иерархических справочников |
| Порядок | число | да | порядок в списках выбора |
| Цвет | цвет | нет | для статусов, критичности и т.п. |
| Действует | флаг | да | недействующую запись нельзя выбрать в новых данных; уже сохранённые значения остаются |

**Простые справочники, которые поставляются с продуктом.** Значения — примеры: заказчик меняет их под себя, кроме системных записей.

| Справочник | Назначение | Как используется | Примеры значений |
|---|---|---|---|
| **Критичность** | Насколько КЕ важна для бизнеса и IT | <ul><li>базовое поле каждой КЕ</li><li>фильтр и сортировка реестра</li><li>колонка в анализе влияния и в блоке «Связанные КЕ» — сразу видно, задето ли критичное</li><li>в roadmap — фильтр рассылки о плановых работах (F-30): «предупреждать только по критичным зависимым КЕ»</li></ul> | Высокая, Средняя, Низкая |
| **Роли ответственности** | Какую ответственность сотрудник несёт за КЕ | <ul><li>матрица ответственности в карточке: роль + сотрудник + основной / замещающий [S2]</li><li>в шаблоне мероприятия: «ответственный по умолчанию — тот, кто в роли X», например периодический пересмотр назначается владельцу системы</li><li>кому слать уведомления о КЕ</li><li>ограничение доступа «только КЕ, где я ответственный» (R8a)</li></ul> | Владелец системы, Владелец процесса, ИТ-сопровождение, Бизнес-владелец |

| **Статусы документов** | Действует ли документ | <ul><li>выбирается у документа</li><li>условия переходов статуса учитывают только документы в статусе «Действующий» — отменённый протокол не откроет ввод в эксплуатацию</li><li>фильтр документов</li></ul> | Черновик, **Действующий** (системная запись), Устаревший (заменён новой версией), Отменён (отозван без замены) |
| **Виды мероприятий** | Что за работа планируется по КЕ | <ul><li>выбирается в шаблоне и в мероприятии</li><li>фильтры сквозного реестра и календаря мероприятий: «все поверки в ноябре»</li><li>**условия переходов статуса**: «выполнено мероприятие вида X»</li><li>виджеты и выгрузки для инспекции: «история периодических пересмотров»</li></ul> | Техническое обслуживание, Поверка, Резервное копирование, Периодический пересмотр, Квалификация IQ / OQ / PQ, **Аттестация данных** (системная: её выполнение с ответом «Карточка актуальна» обновляет дату последнего подтверждения актуальности КЕ, P-24, F-23.BR3 [порция 4]), **Разбор итога** (системная: разбор неуспешного итога, F-05.BR20) [порция 4] |
| **Значения подписи** | Что юридически означает электронная подпись (21 CFR Part 11 §11.50 требует указывать смысл подписи) | <ul><li>в настройках ЭП на действии (переход, выполнение мероприятия, согласование, baseline) выбирается значение</li><li>подписант видит его в окне подписи</li><li>значение сохраняется в подписи и показывается в истории и выгрузках: «Иванов И.И., 10.10.2026 14:05, Утверждаю»</li></ul> | Утверждаю, Согласовано, Выполнено, Проверено, Ознакомлен |
| **Причины отмены мероприятия** | Почему запланированное мероприятие не будет выполнено | <ul><li>обязательна при отмене мероприятия, вместе с комментарием</li><li>пишется в историю КЕ</li><li>отчёты: «какие периодические пересмотры отменены и почему» — на инспекции отмена должна быть обоснована</li></ul> | **КЕ выведена из эксплуатации** (системная запись: её подставляет отмена мероприятий при переходе в конечный статус, F-03.BR19), **Выполнение аннулировано** (системная запись: её подставляет отмена разбора итога при аннулировании выполнения, F-05.BR27) [порция 4, PROPOSAL], Заменено другим мероприятием, Создано ошибочно, Прочее |
| **Местоположения** (иерархический) | Где физически находится КЕ | <ul><li>базовое поле КЕ</li><li>фильтр реестра с вложенными уровнями: «всё в корпусе 2»</li><li>из местоположения — переход к списку КЕ в нём [S2]</li><li>в roadmap — основа QR-инвентаризации (F-24)</li></ul> | Площадка «Москва» → Корпус 2 → Этаж 3 → Помещение 214 → Рабочее место 5 |
| **Роли контрагента** | Кем внешняя организация приходится КЕ | <ul><li>в таблице «Внешние контакты» карточки КЕ (§4.6)</li><li>фильтр «все КЕ поставщика X»</li></ul> | Поставщик, Производитель, Подрядчик |
| **Должности** | Единый список должностей сотрудников | <ul><li>реквизит сотрудника</li><li>пополняется при синхронизации с AD и 1С:ЗУП</li><li>фильтр сотрудников</li></ul> | Руководитель службы ИТ, Системный администратор, Инженер по валидации |
| **Системы-источники** | Внешние системы, из которых приходят внешние идентификаторы КЕ | <ul><li>система-источник во внешнем идентификаторе КЕ (§4.1, F-02)</li><li>сопоставление данных API, импорта и будущего мониторинга с КЕ (W-6a)</li></ul> | Zabbix, AD, 1С:Бухгалтерия |

**Справочники GxP-пакета** (discovery §5.5) — поля карточки компьютеризированной системы:

| Справочник | Назначение | Как используется | Значения |
|---|---|---|---|
| **GxP-значимость** | К какой области регулирования относится система | <ul><li>поле карточки</li><li>фильтр реестра: «все GMP-системы» — первое, что просит инспектор (Annex 11 §4.3)</li></ul> | GMP, GDP, GLP, GCP, GVP, Не применимо |
| **Категория GAMP 5** | Тип ПО по GAMP 5; от него зависит объём валидации: для категории 5 (заказное ПО) — полный цикл, для 1 (инфраструктура) — минимум | <ul><li>поле карточки</li><li>фильтр и отчёт</li><li>администратор учитывает её, когда решает, какие мероприятия и документы обязательны для типа</li></ul> | 1, 3, 4, 5 |
| **Влияние** | Оценка влияния системы на безопасность пациента, качество продукта и целостность данных — три поля с этим справочником | <ul><li>поля карточки</li><li>основа для оценки риска</li><li>фильтр</li></ul> | Прямое, Косвенное, Нет |
| **Риск** | Итог регуляторной оценки риска системы. **Не путать с критичностью**: критичность — важность для бизнеса и IT, риск — последствия для пациента, качества и данных. У системы бухгалтерии может быть высокая критичность и низкий GxP-риск | <ul><li>поле карточки</li><li>фильтр и виджеты</li><li>по нему администратор выбирает интервал периодического пересмотра (обычно 12–36 месяцев); автоматического выбора в v1 нет</li></ul> | Высокий, Средний, Низкий |
| **Статус валидации** | Где система находится в цикле валидации (OQ-4: отдельное поле, изменение — контролируемое, с ЭП) | <ul><li>поле карточки</li><li>виджет «распределение по статусам валидации»</li><li>фильтр</li><li>условие перехода «Ввести в эксплуатацию» в GxP-пакете</li></ul> | Не оценивалась, Не требуется, Запланирована, В процессе, **Валидирована**, **Валидирована с ограничениями** (системные записи пакета: на них опирается условие перехода), Требуется ревалидация, Выведена |

**Удаление записей.** Запись справочника, которая где-то используется (в КЕ, документе, шаблоне, настройке или условии перехода), удалить нельзя — только сделать недействующей (INV-23). Полный перечень того, что считается использованием, — F-19.BR15.

Администратор создаёт свои **простые справочники** для настраиваемых полей (P-14).

**Перечисления продукта** — фиксированные списки, новое значение в которых требует кода:
- типы данных полей;
- виды каналов уведомлений;
- виды таск-трекеров;
- статусы мероприятия, запроса на изменение и задания на согласование;
- действия контрольного следа;
- единицы интервала (день, неделя, месяц, год).

Названия значений перечислений переводятся механизмом локализации.

**Встроенные справочники** описаны в своих разделах: Организации (§2.1), Подразделения (§2.2), Сотрудники (§2.3), Контрагенты и Контактные лица (§2.8), Типы связей (§3.6). Настраиваемые поля у встроенных справочников — позже (OQ-1).

## 2. Организации и люди

### 2.1 Организация `Organization` [R2-2a]
Код (уникальный, неизменяемый), наименование, ИНН (нет), действует (да).
- Измерение данных: у каждой КЕ есть организация-владелец.
- Конфигурация (категории, типы, справочники, роли) — общая на всю установку.
- Ведущая система сотрудников и оргструктуры организации: вручную / каталог / 1С:ЗУП / API (F-14.BR25).
- Ведение, деактивация, удаление — F-13.BR1, BR2; разделение данных — F-28.

### 2.2 Подразделение `Department`
Организация (да), родитель (нет — дерево), код, наименование, руководитель (сотрудник, нет), внешние идентификаторы (нет; ключ синхронизации с 1С:ЗУП), действует.
- Код уникален в организации; родитель — подразделение той же организации; глубина до 15 уровней (F-13.BR3, BR4).

### 2.5 Клиент API `ApiClient` [S1 ¶24]
Название, токены (хранятся только хэши; у токена может быть срок действия или, по явному выбору администратора, бессрочный токен), роль, флаг «изменения по API принимаются без согласования» [S1 ¶22] (в регулируемой категории не действует: изменения по API идут через согласование — OQ-5a [PO 2026-10-14]), ответственный сотрудник, состояние.

### 2.6 Роль `Role` [S1 ¶5–6, R8a, P-21]
| Атрибут | Правила |
|---|---|
| Код, название, описание | код неизменяем |
| Доступные разделы | «Главная», «Реестр КЕ», «Мероприятия», «Справочники». «Мои дела» и профиль — у всех; административные экраны открываются правами на действия (F-13.BR23) |
| Права на действия | перечисление действий из матрицы прав README §5 |
| Права по категориям и типам КЕ | для каждого типа: Create / Read / Update / Delete. **Новый тип — права пустые у всех ролей, кроме администратора** [S1 ¶6] |
| Ограничение по записям | организации (список или «все»); «только моё подразделение» — КЕ, у которых подразделение-владелец — моё или вложенное в него [B2-4a]; «только где я ответственный» |
| Права на ведение справочников | отдельное право на каждый встроенный и каждый простой справочник (D-2a, B2-7a) |
| Видит историю КЕ | отдельное право [S1 ¶5] |
| Системная | роль «Администратор системы» нельзя удалить и лишить прав. Её права — все, кроме права на контактные данные |
| Роль «Ответственный по работе с ПД» | поставляется продуктом, удалить нельзя; единственное её право — «Просмотр и ведение контактных данных», в другие роли оно не включается (F-13.BR13) [B3-5d] |

**Новые роли**: администратор системы создаёт роли с любой комбинацией атрибутов выше, меняет и удаляет их, в том числе роли по умолчанию (README §5).

**Сложение ролей**: у пользователя действует объединение прав всех его ролей, «разрешение побеждает запрет» [S1 ¶5]. Ограничения по записям тоже объединяются: КЕ видна, если её разрешает хотя бы одна роль. Уточнение: право на тип и ограничение по записям сочетаются внутри одной роли: действие над КЕ разрешено, если хотя бы одна роль даёт право на её тип и её же ограничение пропускает КЕ (F-13.BR26).

### 2.7 Замещение `Substitution` [P-2]
Кого замещают, кто замещает, период (с, по), область (согласование изменений и подтверждение мероприятий — одно замещение на оба вида [B4-4, порция 4]; в будущем другие полномочия), комментарий. Действия заместителя пишутся в контрольный след «от имени». Кто создаёт, ограничения и действие — F-13.BR44–BR47. Руководитель сотрудника — руководитель его подразделения или ближайшего вышестоящего (F-13.BR51) [B4-4, порция 4].

### 2.8 Контрагент `Counterparty` и Контактное лицо `Contact` [S2, R13a]
- **Контрагент** — встроенный справочник. Атрибуты: код (неизменяемый), наименование, ИНН (нет), действует.
- **Контактное лицо** — встроенный справочник. Атрибуты: контрагент (обязательно), ФИО, должность (строка), телефон (тип «телефон»), e-mail, действует. Телефон и e-mail — контактные данные (INV-28, F-19.BR22).
- **Внешние контакты КЕ** (§4.6) ссылаются на контрагентов и их контактных лиц.

### 3.5 Статусная модель `LifecycleModel` [R2a, P-1]
- **Статус**: код (неизменяемый), название, цвет, признаки:
  - начальный — ровно один на модель;
  - эксплуатационный — по таким КЕ считаются мероприятия и уведомления;
  - конечный — например, «Выведена из эксплуатации», «Списана».
- **Переход** (`Transition`):
  - из статуса, в статус, название действия;
  - роли, которым разрешён;
  - **условия**: заполнены указанные поля; значение поля — одна из указанных записей справочника (OQ-4); выполнены мероприятия указанных видов, при необходимости не старше N дней; приложены документы указанных видов (P-27). Подробно — F-03.BR11;
  - контролируемый — требует согласования (P-3);
  - требует ЭП со значением подписи;
  - что заполняется при переходе: например, дата ввода в эксплуатацию.

Пример модели «Базового ИТ-пакета» (настраивается): Планируется → Внедрение → В эксплуатации ⇄ На обслуживании → Выведена из эксплуатации → Списана.

Мягкое удаление — не статус, а отдельный признак КЕ (§4.1).

## 9. Жизненные циклы

### 9.1 КЕ: мягкое удаление (независимо от статуса)
```mermaid
stateDiagram-v2
    [*] --> Активна
    Активна --> Удалена: удалить (право Delete, причина)
    Удалена --> Активна: восстановить
    Удалена --> [*]: очистка (администратор - настройка «Разрешить очистку» включена - КЕ никогда не была в регулируемой категории)
```

### 9.2 Мероприятие
```mermaid
stateDiagram-v2
    [*] --> Запланировано
    Запланировано --> Запланировано: выполнено (регулярное) / новая плановая дата
    Запланировано --> Выполнено: выполнено (разовое)
    Запланировано --> Отменено: отменить (причина)
    Выполнено --> Запланировано: аннулировать выполнение (причина) [порция 4]
    Выполнено --> [*]
    Отменено --> [*]
```
Статус срока («просрочено», «близкий срок») вычисляется у мероприятий в состоянии «Запланировано» и только для КЕ в эксплуатационных статусах, не удалённых. [порция 4] Мероприятие из обязательного шаблона без плановой даты «ждёт ввода в эксплуатацию» (F-05.BR4). Выполнение засчитывается с любым итогом (F-05.BR18). У регулярного мероприятия аннулирование возвращает прежние плановую дату и дату последнего выполнения (F-05.BR27).

### 9.3 Запрос на изменение и задания
```mermaid
stateDiagram-v2
    [*] --> НаСогласовании
    НаСогласовании --> Согласован: первый согласующий согласовал → изменения применены
    НаСогласовании --> Отклонён: первый согласующий отказал (комментарий)
    НаСогласовании --> Отозван: инициатор отозвал
    Согласован --> [*]
    Отклонён --> [*]
    Отозван --> [*]
```
Когда запрос выходит из состояния «На согласовании», все его активные задания становятся «Неактуально». Их владельцы получают уведомление о результате, а действия «Согласовать» и «Отказать» им недоступны (P-2, R2-1a).

### 9.4 Пользователь
Активен ⇄ Заблокирован (N неудачных входов или вручную) → Отключён (сотрудник уволен или учётная запись отключена вручную).

 Уточнение (F-13.BR15):
```mermaid
stateDiagram-v2
    [*] --> Активен
    Активен --> Заблокирован: N неудачных входов (временно) / вручную / нет входа N дней
    Заблокирован --> Активен: истёк срок временной блокировки / вручную
    Активен --> Отключён: увольнение / вручную / отключена в каталоге
    Заблокирован --> Отключён: увольнение / вручную / отключена в каталоге
    Отключён --> Активен: вручную (сотрудник работает) / снова включена в каталоге
```
Учётная запись не удаляется (INV-26).

### 9.5 Доставка уведомления
В очереди → Отправлено | Ошибка (после N попыток с паузой) | Нет адреса получателя.
