## 1. Короткий ответ

1. **Да, перенести можно, и сейчас — лучший момент.** Рабочая станция ещё не настроена (см. STATUS), продуктового кода нет. Переезд стоит одну задачу `type:process`.
2. **Кроссплатформенной должна быть не система управления агентами, а продукт.** Агентам достаточно одной ОС, и лучше всего подходит Linux. Работу продукта на Windows доказывает CI на runner'ах Windows и Linux — это уже требование DoD (§4.2). Хуки регламента написаны на Node.js и уже проходят тесты на Linux (`# pass 10`, `# fail 0`).
3. **Рекомендация:** Linux-VM + Claude Code CLI на подписке Max + таймер systemd для `/lead tick`. Managed Agents и Agent SDK для основного цикла пока не берём: пришлось бы переписать оркестрацию, а хуки там не поддерживаются. API-кредиты на Claude Code не распространяются, поэтому они идут на вспомогательные задачи через API и Agent SDK (§5).
4. **Карточки задач в файлах не заводим.** Карточка в стиле Jira у нас уже есть — это GitHub Issue. Предлагаю её усилить: форма Issue с полями, канбан-доска GitHub Projects и механическая проверка статусной модели (§4). Спорю с идеей файлов открыто, доводы — в §4.2.

## 2. Насколько ненадёжна рабочая станция на самом деле

По принципу 2 регламента вся истина живёт в GitHub: Issues, метки, PR, документы. Поэтому падение машины не теряет состояние проекта. Теряется только работа «в полёте»: незапушенные коммиты в worktree и текущий тик. Следующий тик восстанавливает всё по меткам.

Реальные минусы домашнего Windows-ПК:
- перезагрузки после обновлений Windows, отключения света и интернета, сон и гибернация;
- длинные пути, различия Git Bash и PowerShell, нет sandbox для Bash (на нативной Windows его нет, есть только в WSL 2);
- к ПК трудно зайти удалённо;
- ПК делит ресурсы с другими задачами.

VM в дата-центре закрывает все эти пункты. Кроме того, она дешевле круглосуточно работающего ПК.

## 4. Карточки задач

### 4.1 Что у нас уже есть

GitHub Issue — это и есть карточка в стиле Jira:

| Поле Jira | В GitHub Issue |
|---|---|
| Reporter (кто поставил) | автор Issue |
| Assignee (исполнитель) | assignee и метка `area:*` (роль-исполнитель) |
| Created (дата постановки) | `createdAt`, хранится автоматически |
| Status | метка `status:*`; колонка на доске Projects |
| Labels / tags | метки `type:*`, `size:*`, `gate:*`, `phase:*` |
| Description | тело Issue по шаблону `issue-task.md` (Goal, AC, Touches…) |
| Comments | комментарии; отчёты тестировщика и гейтов живут в PR |
| Links, blocked by | `Blocked by #N`, sub-issues, связь PR «Closes #N» |
| History | **timeline**: кто, когда и какую метку поставил или снял — пишет сам GitHub, агент не может её подделать |

### 4.2 Почему не файлы (JSON / MD) в репозитории

1. **Нет единой точки правды для статуса.** Файл карточки меняется в ветке задачи. Пока PR не смержен, `main` и другие агенты видят старый статус. Две параллельные задачи с правкой карточек дают merge-конфликты. Метка Issue меняется атомарно и сразу видна всем.
2. **Историю файла может переписать агент.** Ему достаточно отредактировать поле «история». Timeline GitHub пишет сервер, поэтому аудитор проверяет по нему переходы статусов, которые подделать нельзя.
3. **Дешевле не значит «другой формат файла».** Карточка — это 1–3 тыс. токенов в любом формате. Главная экономия — чтобы проверку статусной модели делал **скрипт, а не модель**. Тогда на неё уходит ноль токенов.
4. **Канбан уже есть бесплатно.** GitHub Projects v2 даёт доску с колонками по статусу, свои поля (Size, Phase, Role) и представления. Доску видно в браузере и в приложении GitHub на телефоне.

Если файлы всё-таки понадобятся (например, при уходе с GitHub), формат — **Markdown с YAML front matter**. Поля в YAML разбирает скрипт, описание и комментарии в Markdown модель читает естественно. В JSON длинный текст требует экранирования переводов строк и кавычек, его хуже читать и человеку, и модели.

### 4.3 Что предлагаю добавить

1. **Форма Issue** `.github/ISSUE_TEMPLATE/task.yml` с обязательными полями: фаза, роль, размер, AC, Touches, Blocked by. Это шаблон `issue-task.md` в виде формы.
2. **Доска GitHub Projects** «KE board». Колонки = статусы `ready → in-progress → testing → rework → review → done` плюс `blocked`. Карточки попадают на доску автоматически по метке.
3. **Сторож статусной модели** — GitHub Action на событие `issues: labeled/unlabeled`, без LLM:
   - ровно одна метка `status:*` и не больше одной `rework-*`;
   - разрешены только переходы из таблицы (например, `testing → review` — только при `PASS` тестировщика на последнем коммите PR);
   - нарушение → комментарий в Issue и метка `process-violation`.
4. **Аудитор** в ретро получает готовый отчёт сторожа и timeline вместо того, чтобы читать всю историю моделью.

Таблицу разрешённых переходов составлю из §4 и §6 регламента. Утверждает ВП в рамках PR `type:process`.

### 5.2 Что из этого следует для нас

1. **Команда агентов (Claude Code на VM) живёт только на подписке.** Кредиты на неё не потратить в принципе. Для запусков без браузера: `claude setup-token` (токен на год) и переменная `CLAUDE_CODE_OAUTH_TOKEN`.
2. **Бот Claude Code Review тоже не может жить на кредитах**, если оставить `claude-code-action`: внутри это Claude Code. Сейчас он работает на подписке через `CLAUDE_CODE_OAUTH_TOKEN`, и это правильно.
3. **Кредиты — для того, что работает через API или Agent SDK.** Кредиты сгорают каждый месяц, поэтому их выгодно использовать, а не копить. Кандидаты по убыванию пользы:
   - **Бот-ревьюер PR на Agent SDK** (TypeScript, в GitHub Actions, модель Sonnet 5.5). Снимает с подписки нагрузку, которая растёт с каждым PR. Делать после фазы 0, когда будет видно, сколько бот тратит.
   - **Пакетные проверки аудитора через Batch API** (−50% к цене): массовая сверка отчётов тестировщика с AC, классификация находок. Результат в течение 24 часов — для ретро это нормально.
   - **Эксперименты с Managed Agents** на одной роли — чтобы через 1–2 фазы решить по данным, а не по документации.
4. **Предохранители на кредитах:** не покупать кредиты сверх включённых и не включать автопополнение. Тогда $100 — жёсткий потолок, сюрпризов в счёте не будет. Под каждого потребителя — свой workspace в Console со своим лимитом расходов и своим API-ключом.
5. **Грубая оценка** (уточним по журналу): цикл задачи на Sonnet 5.5 через API — ~$2–4. Значит, $100 хватит на 25–50 прогонов бота-ревьюера с запасом на эксперименты. Переносить на кредиты основной цикл задач нельзя и не нужно.

### 5.3 Выбор моделей — что взять из рекомендаций Anthropic

- Для агентного программирования Anthropic советует начинать с **Opus 5.5 при effort `medium`** (это его значение по умолчанию) и поднимать effort только там, где падают тесты. Effort часто сильнее влияет на цену, чем смена модели: на `medium` Opus 5.5 теряет ~2.5 пункта качества на SWE-bench Pro при ~70% стоимости `high`.
- **Haiku 5.5** рекомендован для задач субагентов с проверяемым результатом. **Fable 5.1** — только для самых трудных длинных задач, он заметно дороже.
- **Нельзя менять модель, effort и набор инструментов посреди сессии** — это сбрасывает кэш, а кэш — главная экономия (норма — 80%+ входа из кэша).
- Идентификаторы моделей (`claude-opus-5-5` и др.) — это закреплённые версии, они не «обновляются» сами. В автономном тике модель стоит указывать явно (`--model claude-opus-5-5`): тогда поведение воспроизводимо, а смена модели проходит через PR `type:process`.
- Регламент пока не меняем (`model: inherit` у всех ролей, §12.4). Но аудитору в первом ретро — конкретная гипотеза: `task-runner` (диспетчер, без написания кода) перевести на Sonnet 5.5 или Haiku 5.5, а разработчиков — проверить на Opus 5.5 `medium` против `high` по стоимости **решённой** задачи, а не токена.

### 5.4 Что осталось непроверенным

Разрешают ли условия подписки круглосуточную автоматическую работу и каковы точные лимиты Max. Наш режим «тик раз в N минут с лимитами» умеренный, но условия ВП стоит прочитать самому.

## 6. Параметры VM

Расчёт: WIP-лимит 3 задачи. Это до ~7 процессов Claude Code одновременно (штаб, 3 task-runner, вложенные разработчики и тестировщики) по 0.3–0.5 ГБ, 3 worktree с зависимостями, PostgreSQL для интеграционных тестов, Chromium для Playwright по 0.5–1 ГБ.

| Параметр | Сейчас (этапы A–B, документы) | С фазы 0 (код, WIP 3) |
|---|---|---|
| vCPU | 2 | **4** (dedicated или хотя бы не «burstable») |
| RAM | 4–8 ГБ (минимум Claude Code — 4 ГБ) | **16 ГБ** + swap 4 ГБ |
| Диск | 40 ГБ SSD | **100 ГБ NVMe** |
| ОС | Ubuntu 24.04 LTS x64 | то же |
| Софт | git, `gh`, Node.js 22 LTS, Claude Code (нативный установщик) | + Docker Engine (PostgreSQL, сборки), зависимости Playwright |
| Сеть | исходящий HTTPS: Anthropic, GitHub, npm. Входящий — только SSH по ключу | то же |

Проще всего взять VM с возможностью менять тариф без переустановки: начать с 2/8/40, перед фазой 0 поднять до 4/16/100. Ориентир цены у европейских провайдеров — порядка €10–35 в месяц (уточнить у выбранного провайдера).

**Важно про расположение.** VM должна находиться в стране, где сервисы Anthropic официально доступны (список supported countries на сайте Anthropic). Иначе доступ к Claude может быть заблокирован.

**Безопасность VM** (на ней лежат токены GitHub и Claude, а CMDB — чувствительный продукт):
- отдельный пользователь `ke-agent` без sudo; вход только по SSH-ключу; firewall (ufw) — открыт только SSH, лучше через VPN (WireGuard или Tailscale);
- GitHub: fine-grained PAT только на репозиторий `vmeaning/KE` (contents, issues, pull requests, workflows) вместо полного доступа к аккаунту;
- токены — в файле `600`, вне репозитория; в окружении **не должно быть** `ANTHROPIC_API_KEY`, иначе Claude Code молча начнёт тратить API-кредиты вместо подписки;
- автоматические обновления безопасности (unattended-upgrades);
- снапшот VM раз в неделю. Журнал токенов `.claude/logs/` в git не попадает, поэтому его нужно копировать отдельно (например, ежедневно в приватный gist или облачное хранилище).

**Как Юра работает со штабом:**
- интерактивно: SSH + `tmux` + `claude`; или `claude remote-control` в папке репозитория на VM — тогда сессия штаба видна в приложении Claude Code в браузере и на телефоне;
- автономно: таймер systemd запускает `claude -p "/lead tick"` с блокировкой от параллельного запуска (`flock`), лимитом `--max-turns` и журналом в journald. Это замена Планировщика заданий Windows из §12.5. Флаг `--bare` не использовать: с ним токен подписки не читается.
